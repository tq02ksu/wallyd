# ADR-0010 robotd Python 控制隔离与串口所有权（候选，待确认）

> **状态说明**：本条是[开发计划](robotd-development-plan.md) R02 的产出，**proposed**。
> 计划要求「提交一条新 ADR 供确认」——确认之前，Python 代码里**不得**按任何一条候选落实现，
> 也不得把「线程能跑就行」当成结论。现有 `robotd/` 骨架只用 `threading.RLock` 保证
> 「同一时刻只有一个状态写入者」这条不变量，**没有**声称任何时序保证。

## 背景

ADR-0009 接受 Python 作为 robotd 主语言，但明确留下一个未决项：

> Python 的具体控制隔离机制另行设计，不能直接把 Python 线程等同于 Node Worker。

ADR-0008 的 Node `worker_threads` 方案已随语言迁移被取代，但**它提出的要求继续有效**：
快慢分离、单写者、有界背压、停止优先、板侧看门狗兜底。

旧 TS 实现的实际状况（`src/runtime/robot-runtime.ts`，1918 行，单线程事件循环）：

| 关注点 | 现状 | 为什么在 Python 里不能照抄 |
| --- | --- | --- |
| 心跳 | `setInterval(200ms)` 发 `velocity` | Python 定时器在负载下漂移；GIL 下长任务会让它排队 |
| 串口读 | `serial-bridge.py` 子进程 + stdio | Python 可直接持串口，但**同步读会阻塞**调用它的线程 |
| HTTP | 同一事件循环 | 若用同步框架，一个慢请求就会卡住心跳 |
| 抓帧/模型 | `spawn` 子进程 / HTTP + 10s 超时 | 已经是进程边界，风险较低 |
| 停止 | `stop()` 直接写串口 | 必须保证它在任何阻塞下都能插队 |

Python 与 Node 的差异点，正是决策驱动要处理的：

- **GIL**：纯 Python 的 CPU 密集段落会让其他线程只能按 `sys.setswitchinterval()`（默认 5ms）
  的时间片抢占；这不是硬实时保证，但比「完全不能抢占」好得多。
- **阻塞 I/O 会释放 GIL**：同步串口读、`select`、`socket.send` 在等 I/O 时释放 GIL，
  所以「一个线程专做串口」在 Python 里确实可行——但**前提是它不阻塞在别的东西上**。
- **没有等价于 Node worker 的「干净」隔离**：`multiprocessing` 是真正的进程隔离，
  代价是 IPC 序列化与生命周期管理；`threading` 便宜但没有内存隔离。

## 决策驱动

- **停止端到端 ≤50 ms**（契约 §7）。这是唯一不能被牺牲的指标。
- **看门狗 ≤500 ms 由板侧兜底**：host 侧不必做到硬实时，但**必须保证「失活即停喂」**——
  不能出现「管理线程挂了，独立心跳线程还在替它续命」。
- **单写者**：串口与运动状态只能有一个写入者（ADR-0006 / ADR-0009）。
- **可验证**：要能注入「管理阻塞」「控制失活」「队列满」「取消竞争」，并断言不会盲重试运动指令。
- **不为了隔离而引入运维成本**：单机、单串口、两个电机。ADR-0006 已经否决过「为两个电机上中间件」。

## 考虑的选项

### A. 独立控制进程（`multiprocessing` / 独立 `python -m robotd.control`）

控制进程独占串口、心跳、运动状态机；管理进程跑 HTTP/WS 与能力编排，两者用有界队列通信。

- **好**：真隔离。管理侧 GIL 竞争、阻塞 IO、内存泄漏都碰不到控制路径；崩溃可单独重启；
  与「串口唯一持有者」天然一致。
- **坏**：多一层 IPC 序列化与超时语义；`stop` 要走 IPC（多一次跳转，需实测是否吃掉 50ms 预算）；
  进程生命周期与僵尸回收要专门处理；调试更难（跨进程断点）。
- **与既有证据的关系**：旧实现已经把串口放在独立子进程（`serial-bridge.py`），
  说明「跨进程持串口」这条路在本项目**已经被跑通**，不是新风险。

### B. 单进程多线程（串口线程 + 心跳线程 + HTTP 线程池）

- **好**：最简单；`stop` 是同进程内存操作，延迟最低；无 IPC。
- **坏**：GIL 竞争无法完全排除；任何一处忘记释放 GIL 的 C 扩展（Vision、numpy、某些串口驱动）
  都可能把心跳卡住；「控制失活」很难证明——只能靠实测，不能靠结构保证。
- **关键风险**：`pyserial` 的读在某些平台上会持锁；Vision 框架（R15 要用）是 Objective-C 桥，
  GIL 行为未在本项目验证过。

### C. 原生扩展 / 子解释器（`subinterpreters`、C 扩展、Rust 绑定的控制环）

- **好**：理论上最优（真并行、低延迟）。
- **坏**：Python 3.13 的 `subinterpreters` 仍有 C 扩展兼容限制；引入 Rust/C 控制环与
  「Python 降低算法接入成本」的初衷相悖；验证成本远超本期收益。

### 候选结论（**待确认，不是决定**）

倾向 **A（独立控制进程）**，理由按权重排序：

1. **它是唯一能用结构而非实测来证明「管理侧阻塞不影响停止」的方案**。B 只能靠压力测试，
   而计划 R19 要求的是「可复现的时序证据」——结构保证 + 实测 比 纯实测 更容易通过验收。
2. **它与既有实现同构**：串口本来就在子进程里。迁移不是新增风险，而是把边界明确化。
3. **代价可量化**：`stop` 多一次 IPC。若实测发现它吃掉过多预算，退路是
   「控制进程内保留一个本机 Unix socket 的快速停止通道」（仍是进程隔离，但绕开队列）。

**不倾向 B 的核心理由**：本项目最贵的教训都是「看起来并发、实际串行」——
旧实现里 `stop` 在 `approach()` 收尾时发出、却把**下一个**运动任务顶成 cancelled（见
迁移矩阵 §4.3 的同类问题）。线程模型会把这类时序 bug 的排查难度再抬一档。

**不选 C 的理由**：本期收益不抵验证成本，且与 ADR-0009 的「Python 便于算法接入」相悖。

## 决定（候选，待确认）

以下五条是**若采纳 A** 时的完整规定。未确认前不实现。

### 1. 所有权

| 资源 | 唯一持有者 | 其他人怎么用 |
| --- | --- | --- |
| 串口文件描述符 | 控制进程 | 不直接碰；只能经命令/事件 |
| 运动状态机（含心跳开关） | 控制进程 | 管理侧只能请求「启动意图 / 停止」 |
| 板侧应发计数 | 控制进程（从板侧事件读） | 管理侧只读快照 |
| `RobotState` 权威快照 | 管理侧的 `EventKernel` | 控制进程**提交事件**，不写状态 |
| 任务表 | 管理侧 `EventKernel` | 控制进程不知道 `task_id`，只认「意图 id」 |

**注意这条的分界**：状态归并留在管理侧（ADR-0006 的事件循环内核），
控制进程只负责「把板侧事实变成事件」。这样状态仍是单点，且不必跨进程共享可变内存。

### 2. 控制存活条件（不接受无限心跳）

心跳的**唯一续期来源**是「当前存在一条未过期的运动意图」：

```text
意图带 deadline（默认 200 ms）→ 控制进程每 tick 检查：
  now > deadline                → 停止喂狗 + 发 stop + 报 intent_expired
  管理侧超过 N 个 tick 未刷新    → 同上（管理失活等价于意图过期）
```

**明令禁止**：控制进程「自己生成心跳」或「检测到管理侧不在就继续维持运动」。
管理侧失活必须等价于停止——这与板侧看门狗是同一条语义，只是提前了一层。

### 3. 有界队列与停止抢占

- 命令队列容量固定（建议 8），**满时拒绝普通命令**（`E_BUSY`），不阻塞、不无限增长。
- 停止**不走队列**：独立的最高优先级通道（A 方案下是同一条 IPC 上的带外消息，
  或独立 socket）。它的语义是「清空队列 + 立即下发 stop」。
- 普通命令超时 500 ms（与契约一致）；超时**不重发**运动命令。

### 4. 时序（目标值，须 R19 实测）

| 环节 | 目标 | 说明 |
| --- | --- | --- |
| 管理侧收到 `POST /stop` → 控制进程发出板侧 `stop` | ≤50 ms 总额 | 含 IPC 一跳 |
| 控制进程停喂狗 → 板侧看门狗触发 | ≤500 ms | 板侧阈值 300 ms，历史实测约 420 ms |
| host `velocity` 发送频率 | ≥5 Hz | 意图存续期间 |
| 板侧普通命令应答 | 500 ms | 超时不重发 |

**这些是目标，不是现状**。迁移矩阵 §3 已列：Python 迁移后必须复测，通过前不得宣称保证。

### 5. 有序关闭

```text
SIGTERM
  → 管理侧停止受理新请求
  → 请求停止运动（带 deadline，等待板侧应答或超时）
  → 控制进程确认停止或自身退出（退出即停喂狗 → 板侧兜底）
  → 回收桥子进程（语音 / 相机）
  → 持久化运行产物、退出
```

**关机必须先走停止路径**，不能「先关日志、再关串口」——旧实现在
`process.on('SIGINT')` 里 `runtime.stop()` 之后立刻 `process.exit(0)`，
板侧 stop 是否送达**未确认**。Python 侧要等应答或超时，并如实记录结果。

## 后果

### 若采纳 A

- **好**：停止路径与 GIL 解耦，结构上可证明；串口所有权无歧义；控制进程可单独重启；
  与「同一串口只有一个持有者」天然一致；重计算（Vision）放在控制进程外不影响心跳。
- **坏**：多一层 IPC 与超时语义；调试跨进程；`stop` 多一跳需实测；进程回收要专门处理。
- **中性**：状态归并仍在管理侧，控制进程不持有 `RobotState`——这是刻意的，避免双写。

### 若采纳 B（备选，需明确接受以下代价）

- 必须承认「停止时延」只能靠实测保证，无法靠结构保证；
- R19 的故障注入要更严（用 C 级阻塞、长 GC、大 JSON 序列化做压力）；
- 需要在 CI 里保留一条「心跳漂移」回归测试，防止后续引入的 C 扩展悄悄破坏它。

## 怎么验证

**确认前**：本文档评审通过即视为 R02 的「设计结论」成立；实现仍要等确认。

**确认后**（R07/R08/R19 的验收条件，可执行断言）：

1. **阻塞注入**：在管理侧注入 2 s 的 CPU 密集任务（`while time.time() < end: pass`）与
   2 s 的同步文件写，断言脚本仍能 `POST /stop` 并在目标时限内收到板侧应答事件。
2. **控制失活**：`SIGSTOP` 控制进程，断言板侧在 ≤500 ms 内自主停机（仿真用 SimBoard 的看门狗复现）。
3. **意图过期**：管理侧故意不刷新意图，断言控制进程主动停喂狗 + 发 `safety.stopped(reason=watchdog)`。
4. **队列满**：灌入超过容量的普通命令，断言返回 `E_BUSY` 且**停止命令仍能插队执行**。
5. **取消竞争**：同时发 `DELETE /tasks/{id}` 与 `POST /stop`，断言任务终态只提交一次、
   且不出现「停止把下一个任务顶成 cancelled」这类串事件（旧实现踩到过）。
6. **不盲重试**：让板侧 `move` 不应答，断言 robotd **只发一次** `move`，
   然后查询 `status` 判定，不重发。

复现命令与原始日志落 `work/`，结论与分位数写 `eval/`。
