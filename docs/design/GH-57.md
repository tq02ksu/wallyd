# GH-57 结构化停止原因与 safety.* 桥接

## 1. 目标与边界

把“为什么停”从自由文本变成可判定的结构化事实：

- robotd 的 `safety.stop_requested` 必填 `cause` 与 `state`；`detail` 保留给人读。
- robotd 的生产路径能产生全部九种 cause；当前无法自然触发的输入通过
  `App.report_safety_stop()`（Nav/感知/参数校验的停机入口）或 fake transport 进入，
  安全判定仍全部在 robotd。
- agentd 的 `robotd-event-bridge.ts` 消费 `safety.stop_requested`，按 robotd 给出的
  `task_id` 找回对应 run，写入结构化 `blocking_reason`；run 不会被标成 `succeeded`。
- 播报层把 cause 转成人话，不再只说“任务中断了”。

不做：改板侧看门狗时限、改 ADR-0003 停止策略、让 agentd 参与安全决策、
实现完整 Nav/障碍物算法、真机拔串口与物理停机验证（属于 #51）。

## 2. 契约

`contracts/events.json` 新增/更新：

| 事件 | 关键字段 |
| --- | --- |
| `safety.stopped` | 保留旧契约（`reason`/`source`），只说明停止动作发生 |
| `safety.stop_requested` | 必填 `cause`、`state`、`detail`；可选 `task_id` / `run_id` |
| `safety.slowdown` | 仅登记，**只在减速状态变化时发送**（进入/解除各一条），不是逐帧控制流 |

`cause` 枚举：`user_voice` / `user_stop_api` / `obstacle` / `watchdog_timeout` /
`param_out_of_range` / `observation_stale` / `device_lost` / `bridge_exit` /
`internal_error`。

`state` 枚举：

- `confirmed`：板侧确实应答了 stop（或板侧主动上报停机且链路仍可用）；
- `requested`：robotd 已受理，但没有可确认的板侧应答；
- `unknown`：无法确认板侧停稳（链路已断、停止写入失败）。**不得**默认升级成
  `confirmed`；它不是失败，也不是成功，而是诚实报告未知。

`POST /v1/robot/stop` 接受可选 `cause`/`detail`；旧客户端只传 `reason` 时归一成
`user_stop_api`。非法 `cause` 返回 `E_VALIDATION`，不猜默认值。

agentd 侧 `safety.stop_requested` 事件同样必填 `cause`；`StopResult.body_stop`
也带 `cause`，方便 UI 与调用方对齐。

## 3. robotd 产生路径

| cause | 产生路径 |
| --- | --- |
| `user_voice` | agentd 语音快速路由以 `cause=user_voice` 调 `robot_stop` |
| `user_stop_api` | `POST /api/stop` / 直接 stop API（缺省归一） |
| `obstacle` | `report_safety_stop(cause="obstacle")` 或板侧停机 reason=`obstacle` |
| `watchdog_timeout` | 板侧主动停机经 fake/真实 transport 进入 `App._board_event` |
| `param_out_of_range` | `report_safety_stop()` 的越界停机入口 |
| `observation_stale` | `report_safety_stop()` 的过期观测停机入口 |
| `device_lost` | `device.lost(esp32)` → `state="unknown"` |
| `bridge_exit` | 宿主/桥退出时的有序停止 |
| `internal_error` | 内部错误，或板侧上报了无法识别的原因 |

板侧主动停机不反向再发 stop；能否 `confirmed` 只看链路是否仍可用。掉线后即使再收到
板侧上报，也只报 `unknown`。

## 4. agentd 归属规则

事件桥只用 `payload.task_id` 找回 run（`tool_calls.robot_task_id` → `runs.run_id`）：

- 找到且 run 未终结 → `cancelRun(run_id, cause)`，`blocking_reason` 直接是枚举值；
- run 已终结 → 不改状态（事后到达的停止不能把 `succeeded` 回溯改判）；
- 没有 `task_id` → 只记事件，不猜 `activeRun()`。语音“停”本身也是一次 run，
  按活动 run 猜会把停止指令自己取消掉。

安全停止把 run 落成 `cancelled`，不是 `succeeded`。GH-13 仍然规定 `cancelled` 不自动播报；
但 `composeNarrationText` 对 cancelled/interrupted/failed 都会使用 `blocking_reason`
的人话标签，因此“能说出原因”由结构保证，而不是靠在某个调用点补一句。

## 5. 测试映射

| 判据 | 测试 |
| --- | --- |
| 1 必填 cause 枚举、只读 cause | `robotd/tests/unit/test_safety_cause.py`、`robotd/tests/contract/test_contract_parity.py` |
| 2 九种 cause 均可产生 | 同上（`report_safety_stop` + fake transport） |
| 3 掉线必须是 `unknown/device_lost` | 同上，反向断言 `state == "unknown"` |
| 4 板侧停机 `confirmed/watchdog_timeout`，覆盖正常与掉线 | 同上（`SimBoard.sim_board_stop` + `inject_fault(LOST)`） |
| 5 agentd 写 `blocking_reason`、播报可解释、run 非 succeeded | `agentd/tests/unit/safety-bridge.mjs` |
| 6 事件登记、契约生成、事件注册校验 | `npm run contract:check`、`robotd/tests/contract/test_event_registry.py` |
| 7 `safety.slowdown` 只在状态变化时发 | 契约 `notes` + `test_slowdown_contract_is_change_only` |

## 6. 已知限制

- 完整 Nav/障碍物算法未实现；`obstacle` / `param_out_of_range` / `observation_stale`
  目前通过 robotd 内的统一停机入口或板侧上报产生，后续 Nav 直接复用该入口。
- 真机断串口与板侧看门狗物理停机的证据不在本 issue；由 #51 按同一 cause/state 契约收集。
