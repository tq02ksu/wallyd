# GH-48 任务暂停/恢复（robotd 能力面）

## 问题

robotd 只有两种「停」：`robot_stop`（取消，任务终结，不可恢复）与 `audio/mute`
（音频通道闸，不是任务状态）。使用者说「等一下」时，能力面没有可表达的中间态，
agentd 只能取消再重新调用 `robot_follow`——而 `robot_follow` 需要审批，
于是「停一下」→「继续」会再问一次确认，这既不是用户想要的，也不是安全需要的
（目标、距离、速度上限都没变）。

## 决定

### D1：用资源子路径，不用独立动词能力

契约新增两个端点，**不再保留 `task_pause` 之类的独立动词路由**：

```text
POST /v1/tasks/{task_id}/pause    operationId: task_pause
POST /v1/tasks/{task_id}/resume   operationId: task_resume
```

理由：暂停/恢复是**某个任务的状态转移**，不是新的身体动作；挂在任务资源下，
调用方不需要先查「哪个任务」再拼一个全局动词。两者都**不需要审批**：
`resume` 没有改变任何被确认过的参数（目标、距离、速度上限都没变），
`pause` 只降低风险。审批门仍由 `robot_follow` 等动作端点承担。

### D2：任务状态机扩一格，paused 不是终态

```text
accepted → running ─┬─► completed
                    ├─► failed
                    ├─► cancelled
                    └─► paused ─┬─► running   （resume）
                                ├─► cancelled （stop / 暂停超时 / task.cancel）
                                └─► failed    （板侧故障等）
```

- `paused` **不终结**任务：`finished_at` 保持 null，`error` 保持 null。
- `paused` **不进 `superseded`**：任务还在那儿，只是不动了。
- `pause` 幂等：已 `paused` 再调返回当前任务（用户可能连说两次「等一下」），不重复发事件。
- `resume` 幂等：已 `running` 再调返回当前任务。
- 终态任务调用 `pause`/`resume` → `409 / E_STATE`，不复活任务。
- 只允许**运动任务**（`exclusivity: motion`）暂停；语音等 `soft` 任务返回 `409 / E_STATE`。
- 暂停期间运动槽位仍被占用：另一个运动任务返回 `409 / E_BUSY`。这是「还在那儿」的代价，
  也是防止「暂停的跟随」与「新动作」同时存在。
- `resume` 在板侧链路不可用时返回 `503 / E_LINK` 并**保持 `paused`**：恢复意味着
  「身体可以继续动」，联系不上板侧就不能声称已恢复。任务不会因此变成无限期 running——
  这次暂停的截止时间还在，到期照常转 `cancelled`。
- 公开 `Task` 增加可选字段 `pause_expires_at`（Unix epoch 毫秒）；非 paused 时不出现。

### D3：paused 时 `mode` 不是 moving

`RobotMode` 仍只有 `idle | moving | degraded`，但 `derive_mode` 的输入改为
「存在**未暂停**的排他运动任务」。暂停中链路正常 → `mode: idle`（机器人确实没在动），
快照的 `task_id` 仍指向那个任务，调用方据 `GET /v1/tasks/{id}` 区分
「根本没有任务」与「任务暂停中」——**不新增 `mode: paused`**，因为 `mode` 表示身体
是否在动，任务粒度由 `Task.state` 表达。

### D4：暂停 = 速度归零 + 板侧 stop，不需要心跳维持

`pause` 在改任务状态之前**先把停止意图下发板侧**：

1. 校验任务存在、`running`、`motion`；
2. `board.notify("stop", {})`（有序停止，与 `robot_stop` 同一条板侧通道）；
3. 成功后才把任务转 `paused` 并发 `task.paused`。

板侧如果联系不上（无适配器 / 链路未就绪 / 下发异常），**不进入 paused**：
任务按 `failed`（`reason: lost_link`）收尾并返回 `503 / E_LINK` 或 `E_UNAVAILABLE`。
「daemon 以为暂停了、板子还在跑」是不允许的中间态（ADR-0003 失效保护）。

paused 期间 robotd **不发 velocity 心跳**：没有运动意图要维持，板侧保持停止状态，
其本地看门狗（`HEARTBEAT_TIMEOUT_MS=300`，实测 420ms 停机）仍是兜底。
沿 ADR-0003 的口径，暂停不等同于「心跳继续 + 速度 0」——后者会让板子停在
「受控但可能随时接受下一条速度指令」的状态，而当前 robotd 没有可验证的速度闭环实现。
真机上的物理静止延迟按 ADR-0003 的 stop 口径（端到端 ≤50ms 目标）实测记录；
本轮无法上真机 → `pending-hardware`，不估价。

### D5：暂停有上限（默认 120s），超时转 cancelled 并播报

- 配置项 `pause_max_seconds`，默认 `120`，允许 `[1, 600]`，可用
  `ROBOTD_PAUSE_MAX_SECONDS` 或配置文件覆盖；HTTP 不接受调用方自带超时
  （避免把「无限期悬着」写进请求）。
- 到期仍在 paused → 先尽力再下发一次板侧 `stop`（转终态不能只改任务表），
  发 `task.pause_expired{task_id, announced}`，任务 `cancelled`（`reason: pause_timeout`），
  并**尽力播报**固定句子「等太久了，我先停下了。」。
- 播报走 robotd 内部的固定模板系统播报（不是 `robot_speak`，不接受自由文本）；
  音频桥不可用时不伪造成功：`task.pause_expired.announced = false`，日志记录原因。
- 提前 `resume` / `stop` / `task.cancel` 会撤销这次暂停的定时器；每次暂停带一个
  内部 token，旧定时器不会误伤重新暂停的任务。
- 不变量：**paused 一定有截止时间**。如果定时器本身无法建立（内部故障），任务按
  `failed(reason: internal)` 收尾并返回 500，绝不留下一个没有上限的 paused。
  到期收尾时事件与终态分开兜底：`task.pause_expired` 写不进事件日志只影响时间线，
  任务仍按 `cancelled` 收尾——此刻已经没有任何定时器兜着它了。

### D6：安全优先级不变

- `robot_stop` 语义不动：仍是取消。它会把 `paused` 任务也取消（非终态运动任务集合），
  且幂等、无需审批。
- `task.cancel`（`DELETE /v1/tasks/{id}`）同样能取消 paused 任务。
- 板侧看门狗/链路故障仍走既有路径；paused 不引入新的旁路。

### D7：paused 不挡澄清与播报

暂停只改运动任务状态，不动音频通道：`audio.mute`、`speech.listen`、`robot.speak`、
`robot.announce` 在 paused 期间行为不变。暂停不是 mute。

## 事件与 run 侧的映射

robotd 的公开事件词汇是 `task.*`（agentd 的 `run.*` 是另一层，见
`agentd/contracts/events.json`）。本 issue 在 robotd 契约新增：

- `task.paused`（no_state）：`{task_id, capability, pause_expires_at}`
- `task.resumed`（no_state）：`{task_id, capability, paused_ms}`
- `task.pause_expired`（no_state）：`{task_id, announced}`，随后 `task.cancelled{reason: pause_timeout}`

验收判据里「run 侧看到 `run.paused` 而不是 `run.finished`」在 robotd 侧的等价物是
`task.paused`（而不是 `task.cancelled`/`task.completed`）。agentd 的 run 时间线
（`run.paused` 与「继续」的会话上下文）属于 #12（V09）；本轮只把 robotd 事件与
agentd 的 robotd 事件订阅白名单打通，不重写 agentd 的 run 生命周期。

**这条为什么不在本轮做**：agentd 今天**根本没有** robotd 任务 → run 的状态映射——
`task.completed` / `task.cancelled` / `task.failed` 也从不改 run 状态。只补
`task.paused → run.paused` 会造出一个「暂停了却不会恢复/收尾」的半条链路：
`task.pause_expired → task.cancelled` 在 run 侧仍然没人接。要接就得同时定义
完成、失败、取消如何映射（会改变每一次 `robot.speak`、每个能力调用所在的 run），
那是 #12 的会话上下文范围，不是本条能顺手决定的。判据 1 的 robotd 侧判据（`task.paused`
而不是终态事件）已由 `test_task_pause_route.py` / `test_api_http.py` 覆盖；
`run.paused` 留给 #12 接线时与上述映射一起做。

## 审批摘要的风险方向

`contracts/approval-digest.json` 增加 `risk_policy` 说明（不是摘要算法的一部分）：
**降低风险的参数变更（降速、缩短距离/时长）不触发重新签发审批凭据；
提高风险的变更（加速、延长距离/时长、换目标）才触发。** 摘要规则本身不变，
`resume` 也因此不需要新凭据。

## 非目标

- 不做「暂停到条件满足自动继续」（A21）。
- 不做「暂停时原地旋转找人」。
- 不改 `robot_stop` 语义，不让 stop 变成 pause。
- 不实现运动控制闭环/跟随（R15/R17 仍未实现）：`resume` 对已实现的能力恢复任务状态，
  真实速度曲线恢复随能力实现落地。

## 事件序列证据（仿真 / 单进程，板侧为 `FakeBoard`）

用真实 `App` + 内核订阅跑出来的是下面三条序列（`FakeClock` 固定时间，节选 `task.*` / `safety.*`）：

```text
pause → resume（判据 1/2/5）
  task.paused      {task_id: t-0001, capability: robot.follow, pause_expires_at: <now+120s>}
  safety.stopped   {reason: task_pause, source: host, task_id: t-0001}
  task.resumed     {task_id: t-0001, capability: robot.follow, paused_ms: 0}
  任务表仍只有 t-0001；没有 task.started、没有 approval.*（不存在第二次审批）

暂停期间 stop（判据 4）
  task.paused      {…}
  safety.stopped   {reason: task_pause, …}
  task.cancelled   {task_id: t-0001, capability: robot.follow, reason: stop}
  safety.stopped   {reason: stop, source: host}

暂停超时（判据 3）
  task.started     {…}
  task.paused      {…}
  task.pause_expired {task_id: t-0001, announced: false}
  task.cancelled   {task_id: t-0001, capability: robot.follow, reason: pause_timeout}
```

`announced: false` 是这一轮没有装配语音桥时的**如实**结果：桥不可用就不伪造「已播报」，
而取消仍然发生。装配了桥的用例见 `test_pause_expiry_cancels_and_announces_fixed_sentence`。
