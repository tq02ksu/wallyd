# GH-49 澄清闭环：追问要说出口，补充的那句话要能接上

## 1. 问题与证据

GH-27 把 `clarify` / `ambiguous` 从「建一条永不推进的 run」改成「不建 run」，
这是正确的；但 `submitRunRequest()` 返回的 `question` 只进了 HTTP 响应体，
语音链路没有任何代码读它。事件里的 `route.clarify` 也只有 `reason` / `advice`，
没有 `question`，所以用户既听不到追问，也无法在事件里复核「它问了什么」。

同时，澄清没有留下一个「等用户补一句」的状态。下一句话只能作为一条全新的
指令独立路由，缺参指令永远补不完整。

## 2. 决策

### 2.1 追问走系统播报，但正文仍由 robotd 固定模板渲染

`robot_announce` 的 `kind` 增加受限枚举 `clarification`。请求**仍然没有 `text` 字段**，
不接受任意自由文本；agentd 只传结构化字段：

- `action_label`：规则摘要（`FastRule.summary`，有界 80 字符）；
- `missing`：缺失参数字段名（如 `target_track_id`，最多 8 个）；
- `candidates`：歧义候选的规则摘要（最多 3 条）；
- `more`：候选超过 3 条时为 `true`（只念前两条 +「还是别的」）；
- `reason`：`missing_arguments` / `capability_unavailable` / `precondition` / `ambiguous`。

robotd 用固定模板把这些字段渲染成一句话。这样既满足「澄清必须被说出口」，
又不会重开 GH-19 已经堵死的「`robot_announce` 变成免审批 `robot_speak`」的洞。

### 2.2 `route.clarify` 事件带 `question`

登记表给 `route.clarify` 增加 `question`（required），与 `run.waiting_input.question`
同名。`summary` 模板改为 `{question}`；`reason` 变为可选的结构化原因
（开窗原因或收尾原因），不再拿它当面向用户的问句。

### 2.3 有界的「等待补充」窗口，不放进 run 表

新增 `agentd/src/agentd/clarification-window.ts`，只保存**最近一次**澄清的内存状态：

```text
{ prompt, question, missing, candidates, more, fast_rule, expires_at }
```

默认窗口 30s。它不是 run，不占 `activeRun()` 的唯一活动名额，也不写 `runs` 表。
**不改 `runs.ts` 里任何会话上下文结构**（那是 GH-12 的范围）。

语音分发（`speech.final` → `submitRunRequest`，`source: 'asr'`）在路由前处理窗口：

1. 受保护规则（`停`）优先：先关窗并记 `reason: stop`，然后照常走 STOP 旁路；
2. 窗口已过期：关窗并记 `reason: window_expired`，这一句按新指令处理；
3. 用户说「算了 / 不聊了 / 取消」：关窗并记 `reason: user_cancelled`，不建 run；
4. 新句子**单独**就能 `matched`：它是完整新指令，关窗记 `reason: superseded`，正常建 run；
5. 否则视为补充：`prompt = 上一句 + 空格 + 这一句`，关窗后重新路由；
   - 拼接后超过 500 字符：不拼接，记 `reason: prompt_too_long`，用这一句重新问
     （新开一个窗口），避免无限累加；
   - 拼接后仍缺参：按普通澄清路径重新问，开新窗口（每个窗口最多拼一次）。

HTTP `POST /api/run`（`source: 'text'`）不消费窗口；它可能开窗，但只有 `speech.final`
会拼接。这样 UI 的文本请求与语音补充不会互相误接。

### 2.4 歧义候选要念得出来

`matchRoute` 返回的 `candidates` 仍是 `id@version`；`submitRunRequest` 在同一张规则表里
反查 `FastRule.summary`，生成可念的候选清单。问题文本形如：

- 2 个候选：「你是想走到我这儿来，还是想跟随我？」
- 3 个候选：「你是想 A、B，还是 C？」
- 超过 3 个：只念前两个 +「还是别的？」

事件与播报使用同一份候选列表，避免「事件里三个、嘴上说两个」的漂移。

## 3. 流程

```text
speech.final ("过来")
  └─ submitRunRequest(source=asr)
       ├─ matchRoute → clarify(come_here, missing=slot:target_track_id)
       ├─ runs.recordClarification(question)  → route.clarify {question, reason}
       ├─ clarificationWindow.open({prompt:"过来", ...})
       └─ announceClarification(structured) → robot_announce(kind=clarification)
                                                 └─ robotd 模板 → TTS

speech.final ("track:t7", 5s 内)
  └─ submitRunRequest(source=asr)
       ├─ 窗口 fresh；单独路由 "track:t7" → none（片段）
       ├─ prompt = "过来 track:t7"；关窗
       └─ matchRoute → matched(come_here@1) → run.accepted(prompt="过来 track:t7")
```

## 4. 契约变更顺序

1. `contracts/openapi.yaml`：`AnnounceRequest` 增加 `kind=clarification` 与结构化字段，
   `AnnounceAccepted` 允许澄清播报没有 `approval_id`；
2. `contracts/events.json`：`speech.announce_failed.approval_id` 改为可选（澄清播报没有审批 ID）；
3. `agentd/contracts/events.json`：`route.clarify` 增加 `question`（required）与可选 `reason`；
4. 重新生成 `contracts/generated/*` 与 `agentd/contracts/generated/*`；
5. 再改测试与实现。

## 5. 测试计划

| 判据 | 证据 |
| --- | --- |
| 1. 澄清被说出口，事件有 question | `run-request.mjs`：澄清返回后 `announceClarification` 收到 `kind=clarification` 与结构化 `missing`；`route.clarify.params.question` 非空。robotd `test_announce.py`：模板渲染出追问并真的发 `speak` |
| 2. 5s 内补充 → 拼接后命中 fast | `run-request.mjs`：`过来` → `track:t7`，`run.accepted.params.prompt === '过来 track:t7'`，`fast_rule === 'come_here@1'` |
| 3. >30s → 不拼接并留原因 | 同一测试用可注入时钟推进 31s；新句单独成 run，`route.clarify.reason === 'window_expired'` |
| 4. 窗口内「算了」→ 清空、无 run、有原因 | `route.clarify.reason === 'user_cancelled'`，runs 表不变 |
| 5. 澄清期间「停」仍走 STOP 旁路 | `route=fast`、`robot_stop` 被下发、窗口关闭且 reason=`stop` |
| 6. 澄清不占活动名额 | 澄清中立刻说完整指令 → 正常建 run，不抛 `E_BUSY` |
| 反向判据 | 临时删掉「拼接后重新路由」→ 判据 2 红；把窗口改成无界 → 判据 3 红。两处临时改动不提交 |

## 6. 明确不做

- 不做 GH-12 的 N=3 轮上下文；本窗口只服务「同一句话没说完」；
- 不做多轮对话式澄清；一个窗口最多拼一次；
- 不把澄清写进 `runs` 表；
- 不让 Harness 参与澄清判定；
- 不为了播报而调用需审批的 `robot_speak`。

## 7. 与 GH-53（`approval_unheard` / 安全词表）的合并口径

GH-53 在 main 上给 `robot_announce` 增加了 `kind=approval_unheard`、`x-announce-lexicon`
与 `args_summary` 的 60 字上限。本条的 `AnnounceRequest` 是按 `kind` 区分的 `oneOf`
（三种请求的必填字段不同），两边因此不是纯文本冲突，而是**同一段 schema 的两种组织方式**。

合并取并集，不退回扁平 schema：

- `AnnounceRequest` 的 `oneOf` 有三个变体：`approval_repeat` / `approval_unheard` /
  `clarification`；每个变体只允许一个 `kind`，审批两个变体都带
  `x-announce-lexicon: announce-lexicon.json` 与 `args_summary.maxLength: 60`。
- robotd 的 `SUPPORTED_KINDS` 与契约枚举继续**精确相等**（`test_contract_parity.py`），
  并新增一条断言：`approval_unheard` 的必填字段必须与 `approval_repeat` 完全一致。
- GH-53 的两条形状断言（`contracts/tools/check.mjs` 2.7 段与
  `test_announce_lexicon.py::test_openapi_length_and_kinds_match_the_lexicon`）改为
  在 `oneOf` 里定位审批变体后检查，**不变量与强度不变**（每个审批变体都必须带词表标记、
  `maxLength` 必须等于词表上限、两个 kind 都必须出现）；同时兼容扁平形态，防止将来回退。
- 实现层：`render_announcement` 先按词表校验 `args_summary`，`approval_unheard` 只念
  固定收尾句；`render_clarification` 保持 GH-49 的结构化字段渲染，两条路径都不接受自由文本。
