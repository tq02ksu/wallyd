# GH-17 设计：事件归并改成「先算后发」

状态标记：当前口径（实现随本 issue 落地）

## 问题

`EventKernel._emit_locked()` 的顺序是「先耗序号 → 进保留日志 → 归并 → 分发」。
`_reduce()` 一旦抛错，前三步都已经发生：序号花掉、日志留下一条永远不会被订阅者看到、
状态也没按它改的事件；`resume()` 还会把这条事件当成合法增量补发给重连客户端。

结果是 `seq` 只保证「唯一」，不保证「对应一次真实的因果」。这是 #15（设备控制带序号 + 回执）
的前置条件：如果 `seq=7` 可能是失败事件，客户端就不能用「补 seq=7」推理状态。

## 决策

### 1. 两段式：`pending` 工作副本 → `published`

`_emit_locked()` 不再直接写权威状态，而是：

1. `scrub_payload()` 清洗 payload；
2. `state._stage()` 取一份**工作副本**（`copy.deepcopy`，进程内、单写者、小对象）；
3. `_reduce(event_type, clean, staged)` 只在副本上算，权威状态一个字节都不动；
4. 全部算成功后才 `state._publish(staged)`、分配 `seq`、写保留日志、分发。

因此 `pending` 对 `snapshot()` / `resume()` / 订阅者都不可见——不是靠「记得别读」，
而是它根本不在权威对象里；`snapshot()`、`resume()`、`subscribe()` 与 `_emit_locked()`
本来就在同一把 `RLock` 内，工作副本连中途被读到的机会都没有。

失败即丢弃：副本扔掉，`seq` 不消耗，日志不追加，订阅者收不到，`snapshot()` 逐字段不变。

工作副本的成本实测约 `0.1 ms/事件`（`copy.deepcopy` 整个 `RobotStateStore`）；
内核的事件频率是「状态变化」级别（不是 20 ms tick 级别），因此占 tick 预算不到 1%，
换取的是「副本与权威状态绝不共享可变对象」这一眼可验证的隔离。

> 为什么选「工作副本」而不是「把归并规则重写成纯函数」：规则只有 5 条，
> 但重写成「返回变更集」会让 `recompute_mode()` / `_invalidate_pose()` 这类已有受控写入
> 出现第二份实现；副本方案改动面小，且天然覆盖以后新增的规则。

### 2. 失败分类与外部可观测状态

| 失败类型 | 例子 | 序号/日志 | 对外 |
| --- | --- | --- | --- |
| 契约不合法（调用方写错） | `device.lost` 的 device 不在枚举里 | 不消耗、不追加 | 抛 `ValueError`（同时是 `RobotdError`，`E_VALIDATION`/400），并记一条拒绝记录 |
| 归并内部失败 | 注入式故障、规则实现缺陷 | 原事件不消耗、不追加；另发一条 `state.rejected` | 抛原异常；订阅者收到 `state.rejected` |

契约不合法为什么**不**发 `state.rejected`：验收判据 1 要求
`emit("device.lost", device="lidar")` 失败后 `last_seq` 不变、`len(_log)` 不变、
`resume()` 补发 0 条。事件在这一层根本不算「发生过」，发一条事件就自相矛盾。
它被记进内核的拒绝记录（`rejections()`，与 `state.rejected` 的 payload 同形状），
运维/测试能查到「谁写错了事件」，但客户端的事件流里没有凭空多出来的一条。

归并内部失败为什么**要**发 `state.rejected`：原事件已经通过契约校验、调用方以为它发生了，
静默丢弃会让外部永远不知道这次状态迁移没生效。`state.rejected` 自己的写入不经过归并规则
（无状态变更），因此不会递归失败。

`state.rejected` 的 payload 固定为 `{type, payload_keys, reason}`：

- `type`：被拒事件的事件名；
- `payload_keys`：被拒 payload 的键名（排序）；
- `reason`：稳定的原因码（`unknown_device` / `invalid_device_status` / `reduce_failed`）。

**不含 payload 原文**：把被拒的值原样再发一遍，等于绕过 `scrub_payload` 的判断把输入重新发布一次。
键名是契约里的公开字段名，不是用户数据。测试对照
`contracts/events.json` 的 `envelope.forbidden_payload_keys` 断言没有内部字段。

### 3. `subscribe()` 的 backlog 删掉

原注释描述「回放 `seq > 游标` 的日志」，实现里 `cursor = self._seq`，
`ev.seq > cursor` 恒不成立，于是永远空——注释与代码对不上，属于**假语义**。
补发语义已经由 `resume()` 承担（`api/events.py` 里 `subscription.accepted.replayed`
就是 `resume()` 的条数），`subscribe()` 再回放一次只会重复投递。
因此删除 `Handle.backlog`，注释改成「快照即起点，更早的历史由 `resume()` 判定」。
`api/events.py` 原本就没有读 `handle.backlog`，无需改动调用方。

### 4. `snapshot()` 不再写状态

`RobotStateStore.snapshot()` 原先顺手 `self.ts = stamp`，让一次**读**改写了权威状态。
这不影响输出（同一函数里已经用 `stamp` 组装返回值），但会让「失败前后快照逐字段相同」
无法断言。改成只读。

## 契约变更

`contracts/events.json` 新增 `state.rejected`（category `state`）。按仓库纪律：
先改登记表 → `npm run contract:generate` → 测试 → 实现。`docs/spec/robotd-interface-contract.md`
§6.2 的类别表同步登记。

`agentd` 这一轮不订阅 `state.rejected`（它没有对应的 UI 语义）；新增事件类型不改变
它已有的订阅过滤，agentd 行为不变。

## 验收映射

| 判据 | 测试 |
| --- | --- |
| 1. 未知 device 的失败无副作用、不消耗序号 | `test_invalid_device_name_rejected_without_side_effects`、`test_failed_emit_does_not_consume_seq` |
| 2. backlog 语义修正 | `test_subscription_gets_snapshot_and_no_cursor_gap`（并断言没有 `backlog` 字段） |
| 3. `device.reset` 中途失败回滚 | `test_device_reset_failure_restores_pose_and_odometry` |
| 4. 注入式归并失败 | `test_injected_reduce_failure_publishes_state_rejected_event`、`test_pending_state_invisible_during_reduce` |
| 5. `state.rejected` 内容边界 | `test_state_rejected_has_no_payload_values`、契约登记测试 |

## 不做什么

- 不做跨进程两阶段提交：进程内、单线程、单写者，`RLock` 已经保证同一时刻只有一个写入者。
- 不为并发写入设计。
- 不改 `task.*` 的归并（它们本来就不写状态；任务表写入仍在 `new_task` / `finish` 内，
  本次不扩大范围）。
