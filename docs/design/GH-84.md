# GH-84 robotd M0 seam extraction and import gate

## 问题

`EventKernel` 同时持有事件日志与任务表/运动槽位；`App` 同时承担装配、停止、
暂停、音频与标定；`AudioRuntime` 通过 `on_utterance_done` / `on_response_done`
回调直接驱动任务收尾。目标结构里的 Task Executive、Resource Arbiter、
Audio/Safety Word 边界因此不存在，仓库也没有静态模块门禁。

## 范围

只做 M0 需要的 seam extraction：不接真机、不改串口/心跳、不实现
`move_distance`、不实现 Safety Word，不改机器可读契约（OpenAPI/事件枚举/生成物）。
EventKernel 的序号、先算后发、快照与订阅语义保持不变；AudioRuntime 的音频引擎不变。

## 决定

### D1 模块与依赖方向

```text
robotd.api         HTTP/WS 适配面（agent adapter）
robotd.app         Composition Root：装配、启动关闭、设备注入
robotd.safety      停止原因/确认状态、停止编排、板侧停止上报
robotd.task        Task Executive：任务与 ActionEpisode 的状态转移
robotd.motion      Resource Arbiter：base_motion 等逻辑资源
robotd.device      板侧/语音桥适配、标定、仿真板
robotd.core        DTO、错误、RobotStateStore、EventKernel、AudioRuntime
robotd.interfaces  端口协议（Clock / BoardPort / TaskCompletionPort / SystemAnnouncer）
```

依赖只能向上表的下方走（`api` 依赖 `app`，`app` 依赖 `safety`，依此类推）。
`interfaces` 不 import 任何 robotd 模块，是端口层。

### D2 EventKernel 只做事件归并

内核保留：事件校验、归并（`emit`）、原子提交（`commit`）、序号、保留日志、
订阅分发、快照、拒绝记录、`resume`。移除任务表、运动槽位与全部任务方法。

新增两个窄接口：

```python
kernel.commit(event_type, plan)  # plan(staged_store) -> payload | None；None = 不提交
kernel.read(fn)                  # 持锁只读权威 store
```

`commit` 在锁内取 store 工作副本，`plan` 在同一副本上改写 RobotTask /
ActionEpisode / 资源归属，成功后才分配序号、发布状态并分发事件。失败或
`plan` 返回 `None` 时不消耗序号、不进日志、不改状态。

### D3 State Store 是权威记录

`RobotStateStore` 新增权威记录：`tasks: dict[str, RobotTask]`、
`episodes: dict[str, ActionEpisode]`、`resources: dict[str, task_id]`、`next_task_seq`。
`task_id` 与 `mode` 由资源归属和任务记录推导：

- `task_id` = `base_motion` 的持有者；
- `mode` = `derive_mode(link_ready, 存在未暂停的 base_motion 任务)`。

快照结构不变（不新增公开字段），RobotTask/ActionEpisode 仍不进公开 DTO。

### D4 Task Executive 决定转移，Resource Arbiter 决定资源冲突

`TaskExecutive` 是唯一改写任务记录的地方：受理、进度、暂停/恢复、终态、
暂停到期、取消。每个转移都是 `kernel.commit`，所以「决定 + 提交」原子。
`motion = base_motion` 的全进程唯一、soft 能力按 capability 去重，由
`ResourceArbiter.admit()` 在同一个提交里判定；冲突抛 `409/E_BUSY`，不排队。

`accepted → running` 不再是独立写路径：受理即在同一次 `task.started` 提交里
以 `running` 落库（此前 `mark_running` 是不发事件的第二写入点）。公开行为不变：
HTTP 受理后返回的仍是 running 任务，事件流仍只有 `task.started`。

暂停仍先下发板侧 stop 再改任务状态（GH-48 D4）；暂停定时器与到期播报由
Task Executive 持有，播报通过 `SystemAnnouncer` 端口，不直接碰音频实现。

### D5 App 只做 Composition Root

App 保留：配置校验、时钟/板侧/调度器注入、组件登记与回收、启动关闭、
健康与快照投影、仿真板与语音桥装配。停止编排移到 `safety.StopCoordinator`，
暂停/恢复移到 `TaskExecutive`，标定移到 `device.CalibrationService`，
任务收尾策略移到 `TaskExecutive`。HTTP handler 只做参数校验与端口调用。

### D6 AudioRuntime 只报音频事实

`AudioRuntime` 用构造注入的 `TaskCompletionPort` 取代两个裸回调：

```python
port.utterance_finished(task_id, outcome, reason)
port.response_finished(task_id, outcome)
```

`outcome → TaskState` 的收尾策略从 App 移到 `TaskExecutive`（实现了该端口）。
音频层不再持有任务收尾逻辑。`task_id` 仍作为会话关联的**数据**出现在
`speech.*` 事件里（契约如此），但它不再驱动任务状态。

### D7 静态门禁与 legacy allowlist ratchet

`scripts/ci/check_imports.py` 用标准库 AST 检查 robotd 的 import 图，作为
import-linter 的等价离线门禁（本环境无法安装新依赖）。契约：

- 分层：`api > app > safety > task > {motion, device} > core > interfaces`；
- 同一行的模块互不依赖：`motion` 与 `device` 双向都不许 import（同一模块前缀下的
  子模块除外，例如 `motion.arbiter -> motion.types` 是合法的）；
- 显式禁止：`device -> task`、`motion -> api`（agent adapter）、
  `api -> device`（agent adapter 不得触碰设备内部）；
- import 目标按**真实存在的模块**解析：`from pkg import submodule` 与相对导入
  （`from .. import task`）会把 `node.module` 与 alias 名一起展开，避免
  `from robotd import task` 被误当成 `robotd`；`from mod import SomeClass`
  只依赖 `mod`，属性名不会变成幽灵子模块；
- 属性链也算依赖：`import robotd`（或 `import robotd as r`）之后的
  `robotd.task.executive` / `r.task.executive` 会按真实模块里最长的已知前缀
  解析，不能靠「不用 import 语句」绕过；字符串常量里的 `robotd.task`
  （日志名、错误文案）不是 import，不会误报。

允许清单是 `robotd/architecture-allowlist.json`，每条必须写明理由，且
`tests/architecture/test_import_contracts.py` 用基线集合锁死：只能删，不能增；
清单里的条目若已不是真实违规，测试同样变红（必须删除）。

引入时现存违规为 0（抽取后的新模块从第一天起就是干净的），因此清单为空；
ratchet 由「清单 ⊆ 空基线」和负例测试（人为造出三类违规、alias/相对 import、
属性链 import、同层兄弟 import 都必须变红）共同保证；至少一条负例走 `main()`
断言退出码非零，证明 CI 入口会红，而不只是扫描器认得违规。

门禁是静态 AST 分析，只看源码里写死的 import：常规 `import` / `from ... import`
之外，`importlib.import_module("robotd.task")`、`__import__(...)`（含
`import importlib as il`、`from importlib import import_module [as load]` 的本地
写法）也按字面量目标解析成真实模块——这些都是标准库的动态 import 写法，不能成为
绕过分层的后门。目标不是字面量（`import_module(name)`）时静态分析判不出来，不猜、
不误报，仍由 code review 兜底。

另有源码级边界测试（`tests/architecture/test_module_boundaries.py`）：

- `core/kernel.py` 不再定义任务 API；
- `app.py` 不调用任务转移、不实现移动业务；
- `api/http.py` 只经 Task Executive / Safety 端口操作任务与停止；
- `core/audio_runtime.py` 不 import 任务模块、不写任务状态；
- 设备层对象 `SimBoard` / `AudioBridge` / `CalibrationService` 只由 Composition
  Root 构造（`import X as Y` 的别名构造同样会被识别）。

## 行为保持

- `task.*` / `safety.*` 事件名、payload、顺序不变；暂停先停板、停止先取消运动任务；
- 暂停到期与恢复的互斥仍成立（Task Executive 的锁覆盖整段到期收尾）；
- 终态不可回转、`finish` 幂等、软任务按 capability 去重、暂停仍占 `base_motion`；
- 音频断桥 / 打断 / 播报失败仍分别落到 failed / cancelled / completed。

## 判据映射

| 判据 | 证据 |
| --- | --- |
| 三类违规 import 门禁变红 | `tests/architecture/test_import_contracts.py` 负例（直接 import、alias/相对 import、属性链、`importlib`/`__import__` 动态 import、同层兄弟、CLI 退出码） |
| 任务/暂停/停止/音频测试仍绿 | `tests/unit/test_task_executive.py`、`test_task_pause.py`、`test_app.py`、`test_audio_runtime.py` |
| 内核序号/原子提交/快照/订阅未回退 | `tests/unit/test_kernel_commit.py`（成功发布、`plan` 返回 `None`、`plan` 抛错回滚）、`test_kernel.py` |
| 内核/App/音频不再持有业务路径 | `tests/architecture/test_module_boundaries.py` |
| gates 通过 | `scripts/ci/check-robotd.sh`（含新的 import 门禁） |
| allowlist 只减不增 | 空基线 + 棘轮测试 |

## 不做

串口、心跳、`move_distance`、Safety Word、固件、真机；不建 perception /
planning / world_model 等无 M0 行为的空目录；不为未来模块预设空接口。
本设计只产生 L2 架构测试与 L3 fake/sim 回归，不产生 L4。

## 已知残留（不在本轮范围）

- `App._start_board_link()` 与 `App.attach_audio_bridge()` 仍在启动装配路径上直接
  `state._apply_link/_apply_device`（随后才发对应的 `device.*` 事件）。这是既有行为，
  改成纯 `kernel.emit` 会改变启动时序语义，留给后续 `device` 装配收敛。
- `capabilities.py` 仍是未列入分层契约的历史注册表（它只依赖 `core`）；把能力表也
  纳入静态契约需要单独设计，不与本轮 M0 抽取混在一起。
