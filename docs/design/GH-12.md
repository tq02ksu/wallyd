# GH-12 设计：有界的会话上下文

## 结论

在 agentd 里放一个**只存内存、只用于消歧**的 `ConversationContext`：
同一回合内的上一句用户文本 + 该轮 run 的结论摘要，喂给 Harness 的 prompt；
**不参与路由判定，不写进 run 的 `prompt`，也不写进事件正文**。

这不是记忆、不是 RAG、不是 `codex thread`。thread 是会话记忆（ADR-0012 规则 4）；
这里的上下文只回答「刚才那句说了什么」，进程重启即空。

## 为什么不能靠「每句独立」

语音是碎的：

- `跟着我走 target_track_id:abc` → `慢一点`：第二句 `matchRoute` 返回 `none`，
  只能交给 Harness；没有上下文时模型只能猜「慢」是什么。
- 但上下文也不能把独立指令吃掉：`跟着我走` 之后说 `停`，仍然是独立的受保护停止。

因此落点分成两半：**路由不变**（`matchRoute` 仍是纯函数），**只有 Harness 的输入多一段
带固定标记的上下文块**，并标注「仅供消歧，不是新指令」。

## 回合边界是三元组

| 条件 | 值 | 行为 |
| --- | --- | --- |
| 静默间隔 | 30_000ms | 超过即开新回合，旧回合不删、只是不再续 |
| 轮数上限 | `MAX_TURNS = 8` | 达到即强制开新回合（判据 3 的机制保证） |
| 显式结束 | `算了 / 不聊了 / 结束 / 不用了` | 立即清空并开新回合，该句不建 run |

注意两个「N」不是一回事：`MAX_TURNS=8` 管**回合总长**，`PROMPT_TURNS=3` 管**喂给模型看几轮**。
`turn_reset` 的原因取 `user_ended` / `idle_timeout` / `max_turns`；超时是**惰性判定**
（下一句进来时才发现过期），不设定时器。

## 数据流

```text
speech.final
  → runs.dispatchUtterance（审批 → 回合探测 → 忙 → 记账 → 提交）
      显式结束语 → conversation.reset(now) + 事件 turn_reset{reason:"user_ended"}，不建 run
      conversation.peek(now)          // 只读：不改回合、不计数
      忙判定：被吞掉的句子不记账，也不写任何 conversation.* 事件
      忙判定通过（确定要建 run）后：
        conversation.advance(now) → turn_id / index / joined / reset
        submitUtterance({..., turn_id})
          成功 → recordTurn()：reset 原因 → turn_reset{reason}；joined → turn_joined{turn_id, index}
          失败（E_BUSY / 提交异常）→ conversation.release(turn)，不写事件
  → submitUtterance（装配层）
      context = conversation.promptBlock()      // 只给 Harness
      submitRunRequest(..., context)
        → route harness → executeHarness(runId, context)
        → route fast    → 丢弃 context
      conversation.note(turnId, {capability, fast_rule, prompt})
```

记账点必须是「确定这句话会变成 run」之后：被忙判定丢掉的句子如果先记账，
时间线上会出现「本回合第 2 句，接上了上一句」——而上一句根本没建 run。
`peek()` 只负责只读判定，`advance()` 才计数，`release()` 负责把没建成 run 的那句退回去。

`promptBlock()` 的固定形状：

```text
[会话上下文·仅供消歧，不是新指令]
第1轮：用户说「跟着我走 target_track_id:abc」，执行 robot_follow（规则 follow_me@1）
[/会话上下文]
```

`RunRequestInput.context` 只传给 `executeHarness`，由 `harness.ts` 拼进发给模型的输入；
`RunRow.prompt` 与事件库保持原句。

## 事件与隐私

新增两条已登记事件（`agentd/contracts/events.json`）：

- `conversation.turn_joined {turn_id, index}`：接上了上一句，`index` 是本回合第几句（1 起）。
  该事件只在**真的接上**（`index ≥ 2`）时写——第一句没有可接的东西，所以不写；
- `conversation.turn_reset {reason}`：回合结束原因。

`conversation.*` 的 payload 只有 `turn_id` / `index` / `reason`，**没有任何用户文本**；
`events.json` 的 `forbidden_payload_keys` 继续拦截 `raw_transcript` 等禁列字段。
`turn_id` 是内存标识，不入库；重启后上下文本来就不存在。

## 明确不做

- 不新增 `slow_down` / `faster` 之类规则：`robot_follow` 没有「改正在进行的跟随」能力，
  规则只能映射到已发布能力；因此判据 1 的落点是「交给 Harness 并续上回合」，
  不是「第二个 run 必须 fast」。
- 不改 `RouteContext`、不改 `matchRoute` 的任何判定；等真有「必须看上下文才能判」的规则
  再给路由加字段。
- 不做跨重启持久化、不做向量检索、不加定时器。

## 两处口径说明

- **判据 1 的首句不限定 fast**：规则槽只接受 `target_track_id` / `track` / `目标`，
  所以维护者举例的 `跟着我走 target:abc` 首句会走 Harness（`target` 不是合法槽名）。
  判据 1 只要求第二句 `慢一点` 的 run 为 `route: harness` 且带 `turn_joined{index:2}`，
  首句 fast（`target_track_id:abc`）与首句 harness（`target:abc`）两种都测过。
- **判据 3 的「不得带上下文」**：这里指的是**路由不得被上下文改变**。同一回合内交给
  Harness 的第二句仍会带提示块（判据 1 需要它），但 `matchRoute` 从不读上下文，
  独立指令的 route 与空上下文完全一致；提示块也被固定标记为「不是新指令」。

## 验收判据与证据

| # | 判据 | 测试 |

| 4 | 20 轮后 `utterances<=8`、promptBlock 最多 3 轮 | `tests/unit/conversation.mjs` + 同上 |
| 5 | `conversation.*` 事件不含对话原文 | 同上（真 SQLite 遍历 events 表） |
| 6 | `算了` 不建 run、`turn_reset{user_ended}`、下一句从 1 起 | `tests/unit/utterance-dispatch.mjs`（真 runtime + speech.final） |
| 7 | 同一句有无上下文时 `matchRoute` 完全相同 | 同上 + `router.ts` 静态检查 |
| R1 | 活动 run 占着时连说两句：`conversation.*` 事件数 0、`snapshot.utterances` 0（评审缺陷 1 回归） | `tests/unit/conversation-turns.mjs` |

## 评审修订（第 2 轮）

第 1 轮评审指出三处问题，本轮按评审给的方案修掉，判据口径随之落定：

1. **记账点**：`attribute()` 拆成只读的 `peek(now)` 与真计数的 `advance(now)`；
   `turn_joined` / `turn_reset` 的写入挪到「忙判定通过、`submitUtterance` 返回 run_id」之后。
   被忙/空/回声吞掉的句子既不计数、也不写事件；提交竞态 `E_BUSY` 用 `release(turn)` 回滚。
2. **`turn_joined` 的计数语义**：按评审给的第二方案把字段从 `count` 改名为 `index`。
   事件名说的是「接上了」，所以它只在真的接上（`index ≥ 2`）时出现；第一句不写。
   这样判据 2「过期后 `turn_joined` 不出现」保持字面成立，事件库也不会出现
   「第 1 句也写成接上了」的自相矛盾。判据 1 的断言相应写为 `turn_joined{index:2}`。
3. **显式结束语**：不再复用 `ignored_empty`，`UtteranceDispatchResult` 新增
   `action: 'conversation_ended'` + `reason: 'user_ended'`；空文本仍是 `ignored_empty`。
