# GH-12 设计：有界的会话上下文

## 结论

在 agentd 里放一个**只存内存、只用于消歧**的 `ConversationContext`：同一回合内的
上一句用户文本 + 该轮 run 的结论摘要（能力名、命中的规则、已抽取的标量参数）。

它有两个落点，**都只做消歧**：

1. **规则前置判断**（判据 1 的答案）：`matchRoute` 收到的 `RouteContext.previous`
   里有「上一轮是谁在做什么」。上一轮是 `robot_follow` 时，`慢一点` 命中
   `slow_down@1`，直接走 `route: fast`；没有上下文或上一轮不是跟随时，这条规则
   **根本不参与匹配**，句子照旧交给 Harness。
2. **Harness 的提示块**（判据 2/3 的降级路径）：交给模型时带一段固定标记的上下文，
   标注「仅供消歧，不是新指令」。

这不是记忆、不是 RAG、不是 `codex thread`。thread 是会话记忆（ADR-0012 规则 4）；
这里的上下文只回答「刚才那句说了什么」，进程重启即空。

## 为什么不能靠「每句独立」

语音是碎的：

- `跟着我走 target_track_id:abc` → `慢一点`：第二句 `matchRoute` 原本返回 `none`，
  只能交给 Harness；没有上下文时模型只能猜「慢」是什么。
- 但上下文也不能把独立指令吃掉：`跟着我走` 之后说 `往前`，仍然是独立指令，
  路由结果必须与「没有上文」完全一致。

所以纪律是：**上下文只让「修饰性规则」从「不命中」变成「命中」**，不改变任何其他
规则的判定。`matchRoute` 仍是纯函数——上下文通过显式入参进来，不读全局状态、不读时钟。

## 回合边界是三元组

| 条件 | 值 | 行为 |
| --- | --- | --- |
| 静默间隔 | 30_000ms | 超过即开新回合，旧回合不删、只是不再续 |
| 轮数上限 | `MAX_TURNS = 8` | 达到即强制开新回合（判据 3 的机制保证） |
| 显式结束 | `算了 / 不聊了 / 结束 / 不用了` | 立即清空并开新回合，该句不建 run |

注意两个「N」不是一回事：`MAX_TURNS=8` 管**回合总长**，`PROMPT_TURNS=3` 管**喂给模型看几轮**。
`turn_reset` 的原因取 `user_ended` / `idle_timeout` / `max_turns`；超时是**惰性判定**
（下一句进来时才发现过期），不设定时器。

## 数据流

```text
speech.final
  → runs.dispatchUtterance（审批 → 回合探测 → 忙 → 记账 → 提交）
      显式结束语 → conversation.reset(now) + 事件 turn_reset{reason:"user_ended"}，不建 run
      conversation.peek(now)          // 只读：不改回合、不计数
      忙判定：被吞掉的句子不记账，也不写任何 conversation.* 事件
      忙判定通过（确定要建 run）后：
        conversation.advance(now) → turn_id / index / joined / reset
        submitUtterance({..., turn_id})
          previous = conversation.previousRun(now)   // 上一轮能力 + 标量参数；过期/新回合为 null
          context  = conversation.promptBlock()      // 只给 Harness
          submitRunRequest(..., context, previous)
            → matchRoute(prompt, { ..., previous })
                previous.capability === 'robot_follow' → slow_down@1（route: fast）
                其他规则完全不受 previous 影响
            → route fast    → executeFast(capability, args)（slow_down 沿用上一轮目标 + 更低限速）
            → route harness → executeHarness(runId, context)
          成功 → recordTurn()：reset 原因 → turn_reset{reason}；joined → turn_joined{turn_id, index}
          失败（E_BUSY / 提交异常）→ conversation.release(turn)，不写事件
          → conversation.note(turnId, {capability, fast_rule, prompt, args})
```

记账点必须是「确定这句话会变成 run」之后：被忙判定丢掉的句子如果先记账，
时间线上会出现「本回合第 2 句，接上了上一句」——而上一句根本没建 run。
`peek()` 只负责只读判定，`advance()` 才计数，`release()` 负责把没建成 run 的那句退回去。

`RunRequestInput.context` / `previous` 只传给路由与 `executeHarness`；`RunRow.prompt`
与事件库保持用户原句。`RunRequestResult.fast_args` 是**装配层内部字段**，HTTP 路由会剔除，
不进 `RunAccepted` 响应。

## 消歧规则 `slow_down@1`

```text
id: slow_down          version: 1        capability: robot_follow
requiresPreviousCapability: robot_follow
patterns: 慢一点 / 慢点 / 慢一些 / 再慢一点 / 走慢一点 / 放慢一点 / 减速 / 别太快
args: target_track_id ← 上一轮参数（沿用，不重新猜目标）
      max_speed_mps    ← clamp(上一轮速度 × 0.5, 0.05, 0.4)
```

为什么落点是 `robot_follow.max_speed_mps`：

- `robot_follow` 是当前**唯一发布过的速度控制参数**（发起跟随时指定上限）；
  不新增「改正在进行的跟随速度」这类能力面上不存在的端点，也不新增 `slow_down` 能力。
- `0.15 / 0.05 / 0.4` 三个数字不是规则自己的判断，而是契约默认值/边界；
  `tests/contract/router.mjs` 断言它们与 `contracts/generated/mcp-tools.json` 完全一致。
- 上一轮没有可沿用的 `target_track_id` → `contextArgs` 返回 null → 按「没有命中」处理，
  交给 Harness；**绝不**拿空目标或凭空速度去执行。

## 事件与隐私

两条已登记事件（`agentd/contracts/events.json`）：

- `conversation.turn_joined {turn_id, index}`：接上了上一句，`index` 是本回合第几句（1 起）。
  只在**真的接上**（`index ≥ 2`）时写——第一句没有可接的东西，所以不写；
- `conversation.turn_reset {reason}`：回合结束原因。

`conversation.*` 的 payload 只有 `turn_id` / `index` / `reason`，**没有任何用户文本**；
`events.json` 的 `forbidden_payload_keys` 继续拦截 `raw_transcript` 等禁列字段。
`turn_id` 与 `args` 都只活在内存里，不入库；重启后上下文本来就不存在。

## 明确不做

- 不新增 `slow_down` 能力或机器人端点；规则只映射已发布能力与已发布参数；
- 不做跨重启持久化：`turn_id` / `args` 不入库，重启后上下文就是空的，**这是设计，不是缺陷**；
- 不加定时器做 `idle_timeout`：惰性判定，够用且不会有悬空定时器；
- 不做向量检索 / embedding / 长期记忆；
- 不改繁忙纪律：`slow_down` 不是安全旁路，活动 run 占着时这句话仍按忙处理。

## 已知边界（第 3 轮记录）

1. **「改正在进行的跟随」不在本条**：`robot_follow` 只有发起时生效的
   `max_speed_mps`，没有原地调速端点。本条的 `slow_down` 是「沿用同一目标、以更低
   限速重新发起跟随」，并且在 agentd 的忙判定下只能在一轮 run 结束之后落地。
   真正的「暂停/继续、不重签审批地改运行中任务」属于 #48（EPIC #52 已记明 #48 应先于
   或同批于本条）。
2. **`robot_follow` 在 robotd 侧仍是 `UNIMPLEMENTED`**（依赖 R15/R16/R17）。
   本条保证的是**路由与上下文**的判定；执行层会如实失败，不会伪造「已减速」。
3. 与 #49 在 `run-request.ts` / `service.ts` / `tests/unit/run-request.mjs` 有重叠，
   评审建议 #49 先合；本轮未改这两处之外的共享语义。

| R4 | 上一轮不是 `robot_follow` / 没有目标 → `慢一点` 不命中（交给 Harness） | `tests/unit/router.test.ts` |

反向验证（本轮实测后已还原）：

- 去掉 `advance()` 的 idle 判定 → 判据 2 红（5 条断言）；
- 把 `MAX_TURNS` 改成无穷 → 判据 4 红（`conversation.mjs` 3 条 + 端到端 2 条）；
- 去掉 `slow_down` 的「没有目标就不猜」守卫 → R4 红（会拿空目标命中）；
- 把 `slow_down` 的 `requiresPreviousCapability` 改成 `undefined` → R4 红：上一轮是
  `move_forward` 但参数里带了目标时，规则会错误命中并拿非跟随轮的目标去调速。
  `router.test.ts` 用这个例子把「前置判断落在能力上」锁死，而不只是靠「没有目标参数」。

## 评审修订

第 2 轮（已合入本分支）：记账点挪到忙判定之后；`turn_joined` 字段改名 `index` 且只在
真的接上时写；显式结束语用独立 action `conversation_ended`。

第 3 轮：评审指出判据 1 未达成、上下文没有接通到路由前置判断。本轮按评审要求接上
`RouteContext.previous` 并新增 `slow_down@1`。**口径冲突的记录**：第 1 轮的
「开工说明」曾说「不许新增 slow_down 规则（没有改正在进行的跟随的端点）」；第 3 轮评审
则明确要求「`慢一点` 在上一轮是 `robot_follow` 时命中 `slow_down@1`，route: fast」，
并指出「规则不存在，判据 1 无论如何都做不到，这本身要先解决」。本轮以**较新的评审**为准，
选择「映射到已发布能力 `robot_follow.max_speed_mps`」这个落点，并把上面「已知边界」的
两点（忙判定、robotd 未实现）写清楚，避免把它说成「已经能在运行中调速」。
