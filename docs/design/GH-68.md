# GH-68 说话人↔track 绑定与 follow 接缝

## 1. 目标与边界

把「谁在说」与「画面里哪条 track 还活着」接起来，只做**离线可验**的部分：

- `robotd-event-bridge` 转发 `person.appeared` / `person.moved` / `person.lost`；
- agentd 维护一张有界、落库、带 TTL 的 `speaker_id ↔ track_id` 绑定表；
- `follow` 只接受仍然活着的 track；低置信度与多人场景必须澄清。

不做：人体检测、跨帧跟踪、ReID/声纹、第三人称指认、多人会话分离、`interlocutor`
上下文分区，也不修改 `FollowRequest` 的字段。所有验证都通过注入合成 `person.*`
事件完成，不接摄像头，不声明任何真机置信度质量。

## 2. 决策

### 2.1 桥只转发事实，生命周期与限流各归其位

- `person.appeared/moved/lost` 三条事件原样转发进 `EventLog`，桥不做「是否要跟随」
  之类的判断；
- `person.moved` 的 5Hz 上限由 `EventLog` 按契约 `rate_limit` 执行（GH-63 已实现），
  桥不再二次限流；
- 桥同时把 track 生命周期同步给绑定层：`appeared` 登记活体、`moved` 刷新、
  `lost` **先删除绑定再写事件**。事件写入失败不能让一条已经消失的 track 继续可跟随。

### 2.2 绑定表落库、有界、按注入时钟过期

`store.ts` 新增 schema v5 的 `person_bindings`：

| 列 | 含义 |
| --- | --- |
| `speaker_id` | 说话人键；上游未提供时用固定匿名键 `@unidentified` |
| `track_id` | 绑定的跨帧 track |
| `confidence` | 绑定置信度（0–1），**落库**而不是只写日志 |
| `source` | `doa` / `visual_anchor` / `explicit`，**落库** |
| `bound_at` / `expires_at` | 注入时钟域内的毫秒时间戳 |

约束：

- 最多 32 条绑定，超限淘汰最早建立的条目；活 track 最多 64 条；
- 读取时同时校验 `expires_at` 与 track 是否仍活着；过期/悬空条目就地删除；
- `person.lost` 按 `track_id` 删除全部绑定（有索引），不留悬空引用；
- 匿名键与任何真实 `speaker_id` 不相等，因此匿名绑定不会跨到之后出现的有名说话人。

### 2.3 门限与 TTL 是配置，不是分支深处的魔法数

`AgentdConfig` 提供三个可配置值（CLI 同名开关）：

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| `followBindingTtlMs` | `60000` | 绑定有效期；到点自动失效 |
| `followBindingMinConfidence` | `0.5` | 低于该值的绑定不得直接下发 follow |
| `followBindingSingleTrackConfidence` | `0.6` | 画面里恰好一条活 track 时自动绑定的置信度 |

单条自动绑定记为 `source: visual_anchor`。这是一个**显式声明的策略值**，不是检测器
分数，也不是新的「唯一推断」来源；门限调高到 0.6 以上时，同一单人场景也会如实澄清。

### 2.4 follow 接缝

`matchRoute` 仍然只认显式槽位。未写目标的 `follow` 会落成「缺
`slot:target_track_id`」，随后由 `run-request` 在澄清之前查绑定表：

1. 画面里有 ≥2 条活 track → `route.clarify`，`reason: ambiguous`，候选最多前两条
   + 「还有别的」。**这一步优先于已有绑定**：单人时刻自动建立的绑定不能当成
   「多人场景下已经确认了是谁」；
2. 恰好一条活 track，且当前说话人有有效绑定、`confidence >= 门限` → 带上绑定目标；
3. 恰好一条活 track，但绑定置信度低于门限 → `route.clarify`，`reason: precondition`；
4. 恰好一条活 track 且没有有效绑定 → 立即绑定（`visual_anchor`，0.6）并带上目标；
5. 显式 `target_track_id`（或上一轮沿用的目标）指向**观测过、随后 `person.lost`**
   的 track → `400 / E_VALIDATION`，错误信息说明「目标已离开画面」，不按 `target`
   静默兜底。从未观测过的 track 是 `unknown`，不是 `dead`：沿用 GH-68 之前的行为
   放行（见 2.5）。

显式点名一条活 track 时，绑定证据来源记为 `explicit`，置信度 1。

### 2.5 接缝：`unknown` 不等于 `lost`，`followTargets` 省略时整段不生效

track 存活被明确拆成三种状态：

| 状态 | 判据 | `follow` 行为 |
| --- | --- | --- |
| `live` | 收到过 `person.appeared` 且尚未 `person.lost` | 正常下发；显式点名时 `bindExplicit` |
| `known-lost` | 观测过，随后收到 `person.lost` | `400 / E_VALIDATION`（`reason: target_gone`） |
| `unknown` | 从未观测过 | 放行，**不拒绝**；也不写绑定 |

两条接缝约定：

1. **只有证据能证明「死了」才拒绝。** 拒绝路径由 `isTrackKnownLost()` 回答；
   不能用 `!isTrackLive()` 代替——那会把「没数据」当成「数据说它死了」。
   直接 `POST /api/run`（旧客户端、夹具、纯路由单测）带一个从未出现过的
   `target_track_id` 时必须照旧 `200/fast`，例如 `approval-settle.mjs` 的
   `过来 track:abc`。
2. **`followTargets` 省略时整段跳过。** 没有绑定表就没有「track 还活着」这个前提，
   自动绑定与存活校验都不启用，行为与 GH-68 之前逐字一致。

判据 2 的强度不因此变弱：显式的、绑定的、上一轮沿用的目标一旦被 `person.lost`
证明失效，仍然是 `400 / E_VALIDATION`。`follow-binding.mjs` 用三段接缝用例锁住
这条约定（未注入 / unknown / 观测后 lost），把 `isTrackKnownLost` 换回
`!isTrackLive` 会让 unknown 那段变红。

## 3. 验证记录（离线）

主用例：`node --experimental-strip-types agentd/tests/unit/follow-binding.mjs`

| 判据 | 证据 |
| --- | --- |
| 1 桥接生效 | 注入 `person.appeared` → 事件库有 `person.appeared`（测试打印 JSON 原文）；同一秒 7 条 `person.moved` → 入库 5 条、丢弃 2 条 |
| 2 lost 失效 | 绑定 `track_9` → `person.lost{track_9}` → 绑定行删除 → `follow track:track_9` 返回 `E_VALIDATION`，不建 run |
| 3 低置信度 | 绑定 0.2 + 默认门限 0.5 → `route.clarify`（`reason=precondition`），无 `robot_follow`；把门限设为 0 后同一条绑定直接命中 fast，即反向判据 |
| 4 多人 | 两条活 track → `route.clarify`，事件 `data.candidates` 正好两条，且没有绑定、没有 `robot_follow` |
| 5 单人 | 仅一条活 track → 直接命中 fast，绑定记录 `source=visual_anchor`、`confidence=0.6` |
| 6 TTL | 时钟推进 60s+1ms → `bindingFor` 为 null，库内条目删除 |

辅助回归：

- `follow-binding.mjs` 还断言 `NODE_EVENT_TYPES` 订阅包含三条 `person.*`，并验证新的
  `speaker_id` 不会沿用其他说话人的绑定；
- `follow-binding.mjs` 的「判据 2 接缝」三段：`followTargets` 省略 + `track:abc`
  → `200/fast`；注入绑定层但 track 从未观测 → `200/fast` 且不写绑定；同一 track
  先 `appeared` 再 `lost` → `400/E_VALIDATION` 且不建 run。把拒绝条件写成
  `!isTrackLive` 时中间那段变红，恢复 `isTrackKnownLost` 后全绿；
- `npm --prefix agentd run -s typecheck`：pass；
- `npm --prefix agentd run -s test:unit`：新增 `follow-binding.mjs` 后 22 项，除 `http.mjs`
  在本沙箱 `listen EPERM` 外全部通过；
- `npm run -s contract:check`：pass（本轮未改任何契约源或生成物）；
- `utterance-dispatch.mjs` 的审批用例补注入 `person.appeared{track_id:"abc"}`：显式目标必须
  是观测过的活 track，这是 GH-68 的新前置条件。

## 4. 明确不做 / 后续

- 真实 track 的生产者（检测 + 跨帧跟踪）仍属于 hardware 票；
- 真实置信度质量只能真机相机验证，本条不声明；
- `interlocutor` 会话主体与上下文分区属于 #50 第三段，本条不碰上下文分区；
- 多人「该听谁的」策略属于 #70，本条只实现「多人时不绑定、走澄清」这条最保守行为。
