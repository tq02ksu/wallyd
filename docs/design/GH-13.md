# GH-13 run 结论播报：接上 speak 与打断语义

## 1. 目标与边界

把「run 结论」与「robotd 播报」之间缺失的一段接上：

- run 进入终态后，由 agentd 取**执行事实**组成一句话，交给 `robot_speak`；
- 播报前用 `RobotdEventBridge.noteSpeak(task_id, text)` 留底（事件里只有 task_id，没有文本）；
- `speech.tts_cancelled {reason:"barge_in"}` **不改 run 状态**：run 已执行完，
  只把 `run.narration` 标成 `interrupted`；
- 同一 `run_id` 至多播一次；
- 播报失败（robotd 不可达）只记 `speech.speak_failed`，run 仍是 `succeeded`。

不做：流式边生成边播、多音色/情绪、改 `robot_speak` 请求形状。

## 2. 凭据：一次性、30 秒、只绑定 text

`robot_speak` 带 `x-requires-approval: {params: [text]}`。agentd 的 `speak()` 每次播报
**现签一张凭据**（`mintApprovalCredential`）：

- `capability = "robot_speak"`；
- `args_digest` 只覆盖 `text`（契约 `approvalParams`，其它字段按规则排除）；
- TTL = 30 000 ms（`MAX_CREDENTIAL_LIFETIME_SECONDS` 是 300 s 上限，不是目标值）；
- nonce 单次消费：同一 run 重播会**重新签**，不复用旧凭据/nonce。

这不等于「用户批准了播报」：凭据是 agentd 签发的执行凭据，`issuer` 恒为 `agentd`；
用户审批门与执行凭据门是两件事（ADR-0007）。不给 `/v1/robot/speak` 开免审批口子。

## 3. 数据模型

`runs` 增加三列（schema v2）：

| 列 | 语义 |
| --- | --- |
| `result_summary` | 执行步骤/工具结果归纳的「做了什么」。当前 fast 路由不写，留空时回落到最后一步 `note`。**不得由模型推理正文填充。** |
| `narration_requested_at` | 播报请求的原子认领时间。非空 = 这个 run 已经请求过播报，重放必须跳过。 |
| `narration` | 播报结果：`spoken` / `interrupted` / `failed`；null = 还没结果或不需要播。 |

`RunSummary.narration` 暴露 `narration`；`RunResult.summary` 暴露 `result_summary`。

**run 状态与 narration 完全解耦**：narration 的三种结果都不写 `runs.status`。
判据 2 的「run 仍 succeeded」由结构保证，而不是靠调用点自觉。

## 4. 触发与幂等

`RunService` 在事务提交后的 `notify(seq)` 里检查事件类型：
`run.finished` 且 outcome ∈ {succeeded, failed, interrupted, outcome_unknown} 时回调
`onTerminal(run_id)`。这一处覆盖 `transition`、审批超时/拒绝、启动对账等所有终态路径。

- `cancelled` **不播报**：用户说「停」/取消是安全旁路，停止后紧接着念一句「没做成」既吵又危险。
- `RunNarrator.narrate(runId)` 先用条件更新认领：
  `UPDATE runs SET narration_requested_at=? WHERE run_id=? AND narration_requested_at IS NULL`。
  只有赢家调用 `robotd.speak()`，因此同一 run 的重放/并发都只播一次。
- 认领后进程崩溃不会自动重播（at-most-once 优先于「一定播出」），这是有意的取舍。

## 5. 文本来源与截断

优先级：

1. `runs.result_summary`；
2. `run_steps` 中按 `idx` 最后一条非空 `note`；
3. 兜底短语。

兜底必须诚实：

- `succeeded` → 「做完了」
- `failed` → 「没做成，原因：<blocking_reason 或 执行失败>」
- `interrupted` → 「没做成，任务中断了」
- `outcome_unknown` → 「已经发出动作，但结果没确认」

绝不读取 `runs.prompt` 或任何模型输出作为播报正文；只念执行事实。

契约 `SpeakRequest.text.maxLength = 500`。超过时按码点截到 496 个字符再追加
`…后面略`（总长 ≤ 500），不返回 400。

## 6. 事件

新增 `speech.speak_failed`（`speech` 类，warning）：`reason` 必填，`run_id` 走事件信封。
`speech.spoken` / `speech.speak_cancelled` 已由事件桥在 `tts_finished` / `tts_cancelled`
时写出，本设计只新增 `onSpeechOutcome` 钩子把这些终态关联回 run 的 narration。

## 6b. ASR final 的分发器（判据 7/8）

事件桥的 `onUtteranceHeard` 原来被审批 settle 独占。现在统一交给
`RunService.dispatchUtterance()`，顺序固定：

0. 空文本 / `echo: true` → 记 `observation.speech_ignored {reason:"echo"|"empty"}`，
   **不建 run、不 settle 审批**（自听里的「确认」不能批准机器人自己念的内容）；
1. 有 `waiting_confirmation` 窗口 → 交给 `settleApproval` 并吞掉这条 final；
2. `activeRun()` 存在 → 记 `observation.speech_ignored {reason:"busy"}`，不排队、不建 run。
   **例外**：命中受保护规则（`stop_robot`）的 final 放行到提交入口——停止是安全旁路，
   语音不能比 `POST /api/run` 更弱；判断复用 `router.ts` 的同一张规则表；
3. 兜底 → 装配层注入的 `submitUtterance`（走 `submitRunRequest`，与 `POST /api/run`
   同一套路由/审批/幂等；幂等键 `asr:<utterance_id>`）。

顺序 1 必须先于 2：`waiting_confirmation` 的 run 本身就是活动 run，先问忙会把「确认」
当成新指令挡掉。分发器不解析意图——意图仍归 `matchRoute`。

## 8. 第二轮：CI 退回的三处修正

上一轮 `agentd` lane 红在 `tests/unit/approval-settle.mjs`。三处都在这份测试里，
外加一处由此暴露的 `runs.ts` 真缺陷。

### A1 复述路径的 `robot_speak` 断言改成有范围的

原来的 `!robotdCalls.some((c) => c.path === '/v1/robot/speak')` 是**整份测试**不许出现
speak，而 GH-13 之后 run 终态就是要 speak。现在拆成两侧：

- 复述阶段（`openWindow` 之后、确认之前）断言 `speakCalls().length === 0`——
  run 还没到终态，没有东西可播；
- run 走到 `succeeded` 之后断言**恰好一次** `speak`，并检查
  `X-Wally-Approval` 非空、凭据 `capability === "robot_speak"`、正文等于
  `composeNarrationText(run, steps)`（即只来自 `result_summary` / step note / 兜底）。

同时把判据 1 补成端到端：拿 speak 的 `task_id` 回灌
`speech.tts_started` / `speech.tts_finished {chunks:2, played:2}`，断言
`run.narration === "spoken"`、`run.status` 仍是 `succeeded`、事件库出现关联该 run 的
`speech.spoken`。`capability` 不在请求体里（请求体只有 `text` 等能力参数，路由由
`/v1/robot/speak` 决定），所以断言落在凭据 payload 上。

### A2 回声断言之前读错了事件

退回意见写的是「桥从 `speech.final` 读 `aec_erle_db`」，实测不是：
`contracts/events.json` 里 `speech.started` 才有 `aec_erle_db`
（`speech.final` 的 payload 只有 `utterance_id/text/stop_reason/no_speech`），
`RobotdEventBridge.onStarted→onFinal` 也是从 `speech.started` 取事实，
GH-11 设计 §规则 6 同样这么写。所以 `utterance()` 一直喂的是**生产路径**。

真正的问题在**断言看错了事件**：回声被分发器在 settle 之前拦下，写的是
`observation.speech_ignored {reason:"echo"}`，不会走到 `settleApproval`，
因此 `approval.ignored` 一条都没有。旧断言读 `approval.ignored` 永远拿到 `null`，
而紧跟的「回声不让 run 推进」因为路径没被观测到而**假绿**。

现在断言：`observation.speech_ignored` 恰好一条且 `reason === "echo"`；
`approval.ignored` 计数不变（证明没进 settle）；run 仍 `waiting_confirmation`；
审批仍 `waiting`。反向验证（把 `erle` 由 1 改成 30，等于抽掉回声证据）这条用例
**五项全红**，包括「回声不让 run 推进」——说明它测的确实是判定本身。

同一门限另在 `utterance-dispatch.mjs` 里有一条不需要网络的用例（低 ERLE → echo 忽略；
高 ERLE → 照常提交），便于在没有回环 bind 的环境里做同样的反向验证。

### A3 每段开跑前先清掉活动 run

`E_BUSY` 的来源是上一段留下的非终态 run（判据 9 之后那句「确认」在窗口已死时会
按分发规则成为一条新指令，落成一个 `accepted` run），随后 `runId` 是 `undefined`
被绑进 SQL，才出现那条 `Provided value cannot be bound to SQLite parameter 1`。

修法按退回意见的第 1 条：`submitFastRun()` 先 `ensureIdle()`——有活动 run 就
`cancelRun()` 并等到 `cancelled`；等不到就明确报错退出。另外 `runId` 不是字符串时
立刻打印响应并 `exit(1)`，不让它进 SQL。判据 8 段结束时也等到 `cancelled`。

### 由此暴露的真缺陷：过期窗口的迟到「确认」丢了账

分发器只处理 `waiting` 的审批，而 `latestApprovalForVoice()` 特意也会返回 5 分钟内的
`timeout` 审批（给「迟到的确认」留审计）。两者不一致 → 迟到的「确认」被当成新指令提交，
`approval.ignored {reason:"expired"}` 不再产生（判据 3/4 因此红）。

`runs.ts` 的修法：对**刚过期且这句话确实像审批回答**（`classifyApprovalUtterance`
不是 `none`）的 final，仍走 `settleApproval`（结果是 `expired`，写 `approval.ignored`）
并吞掉；同时排除受保护规则（「停」任何时候都照常提交，不能被一个死窗口吞掉）。
普通指令在过期后照常提交——不能用已死的窗口把用户堵 5 分钟。`utterance-dispatch.mjs`
新增了这一正反两面的用例。
