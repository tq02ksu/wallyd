# GH-19：审批复述的系统播报路径

状态：已实现（契约 + robotd + agentd 时序）。对应 issue：审批复述必须走系统播报，
不能调用 `robot_speak`，否则审批递归。

## 问题与约束

审批复述是审批链路的一部分，不是普通播报。若用 `POST /v1/robot/speak`
（`x-requires-approval: true`）来念「我要往前走两步，确认吗」，就会在
「等待确认」里再触发一次「等待确认」。

同时，使用者只有语音与摄像头，没有屏幕和键盘：机器人必须能把动作念给用户听，
而且必须知道**真的念完了**，才能打开限时确认窗口。

## 决策：一条契约可见的 HTTP 系统路径

新增 `POST /v1/robot/announce`（`operationId: robot_announce`）：

- **不带** `x-requires-approval`：它是审批链路本身；
- 标 `x-mcp-exclude: true`：它不是 Agent 可调用的能力，不进入
  `contracts/generated/mcp-tools.json`（工具面保持 14 项）；
- 只有一条这样的路径，不另开「内部方法」后门。

没有选择「只传 `approval_id` + `kind`，由 robotd 查审批记录渲染」：审批状态归
agentd（ADR-0007 / AGENTS 的 ownership 规则），robotd 再存一份就是第二份会漂移的真值。
因此请求带结构化字段，由 robotd 用固定模板渲染。

## 请求形状与风险边界

`AnnounceRequest` 故意**没有 `text` 字段**：

| 字段 | 约束 | 来源 |
| --- | --- | --- |
| `approval_id` | 1–64，`^[A-Za-z0-9_.:-]+$` | agentd 审批记录 |
| `kind` | 枚举，仅 `approval_repeat` | 固定模板种类 |
| `action_label` | 1–80，单行 | 审批记录 |
| `args_summary` | 1–200，单行 | 审批记录 / `approval.args_summary` |

robotd 渲染固定模板：

```
请确认：{action_label}。参数：{args_summary}。确认请说“确认”。
```

未知字段、`text`、未知 `kind`、控制字符/换行一律 400。这样它不能直接念
任意用户文本，无法成为 `robot_speak` 的免审批版本。残留风险是：持有回环 HTTP
访问权的程序仍可让机器人念一段受长度限制的摘要；本条的信任边界是「本机 agentd」，
不是「任意本机进程」。进一步收紧需要审批记录签名或共享存储，不在本条范围。

## 事件与因果顺序

- `speech.tts_started` / `speech.tts_finished` / `speech.tts_cancelled` 在系统播报时
  额外携带 `approval_id`、`kind`、`task_id`；
- issue 里说的 `tts_played` 在本仓库契约中的实际事件名是 `speech.tts_finished`
  （payload 带 `played`；agentd 再映射为 `speech.spoken`），没有另造同义事件；
- `speech.tts_finished` 是「真的播完了」的唯一信号，`robot_announce` 的 200 只表示受理；
- 播报失败（桥不可用等）发 `speech.announce_failed`，不允许静默失败；
- agentd 收到成功的 `speech.tts_finished` 后才调用
  `RunService.openConfirmationWindow()`，在同一事务里写
  `approval.status = waiting`、`run.status = waiting_confirmation`，并发出
  `approval.waiting` 与 `run.waiting_confirmation`（带 `window_opened_at`）。

`run.waiting_confirmation.window_opened_at` 是 #11 判断「这句『好』是否在本轮复述之后」
的必要证据；没有它就无法区分对本次复述的回应与对上一件事的回应。

### 终态事件丢失与重复事件

「以事件为准」还有两个必须显式处理的边角，否则会把 run 留在半路：

1. **完成事件可能先于 HTTP 响应到达**。`robotd.announce` 的响应与
   `speech.tts_finished` 走两条连接，没有顺序保证。审批先落库（`persisted`），
   所以事件可以先开窗；随后到达的响应只补 `prompt_text`，不会把 `waiting` 回退成
   `announced`（状态更新带 `status = 'persisted'` 条件）。
2. **完成事件可能丢失**（WS 断线、桥异常退出但没发终态）。受理后启动
   `announceTimeoutMs`（默认 30s）计时；超时仍停在 `persisted`/`announced` 时按失败收尾，
   发 `approval.unavailable {kind: "announce_timeout"}` 并结束 run。**不允许**一个 run
   永远等一条不会来的事件。

开窗与中止都使用**带状态条件的 UPDATE**（`status IN (...)`）并检查 `changes`：
重复的 `tts_finished`、迟到的取消、并发事件只有一个能赢，确认窗口不会被写两次。
`kind` 缺失或不是 `approval_repeat`、或审批 ID 未知的终态事件一律忽略并留日志，
不能让别的事件代开确认窗口。

## stop 与失败

- `robot_stop` 免审批，但会调用 `AudioRuntime.abort_response("stop")`：
  立刻清空当前 response、发 `speech.tts_cancelled`（带 `approval_id`）、
  并通知桥 `stop_speak`；
- agentd 收到取消后走 `abortApproval()`：**不开窗**；由 stop 引起时 run 记
  `cancelled`，由播报故障引起时 run 记 `failed` 并写 `approval.unavailable`；
- 窗口开启后即使收到迟到的完成事件也不会改回 `waiting_confirmation`（终态不可改写）。

## 已评估但保留的设计取舍

机器人审阅指出「`action_label`/`args_summary` 仍由调用方提供，等于受限的自由文本」。
这是有意保留的取舍：robotd 不持有审批状态（ADR-0007 / ownership 规则），只给
`approval_id` + `kind` 时它没有任何可念的内容；而 #11 要求复述动作与关键参数。
当前边界是：没有 `text` 字段、未知字段 400、单行、长度上限（80/200）、
固定模板包裹。它比 `robot_speak` 窄得多，但不是零风险；真正的零风险版本需要
审批记录签名或共享存储，属于 #18/#11 的凭据体系，不在本条范围。

「审批播报没有接进 Agent」的审阅项经核对为误报：`service.ts` 的 `executeFastRun`
在 `tool.requiresApproval` 分支里先 `createApproval`，再 `approvalAnnouncer.announce()`。
当前仓库只有快速规则这一条会产生审批的路径；托管 Harness 的工具调用审批尚未实现。

对「同一审批第二次 `announce()`」保留 fail-closed：状态为 `persisted`/`announced`
时允许重发（用于 HTTP 响应丢失后的重试），但若第一轮其实仍在播，robotd 会回
`409 E_BUSY`，agentd 按播报失败收尾（`run.failed` + `approval.unavailable`）。
宁可让 run 失败，也不制造第二个确认窗口或让用户被问两次；代价是这种情况下需要
重新发起这次动作。当前流程每个审批只调用一次 `announce()`，这条路径不可达，
但顺序纪律留在文档里，避免将来加重试时把 409 当成成功。

## 与 main 的合入（GH-4 / GH-17）

`main` 在变基之后新增了语音桥「拾音 / 出话」双管道拆分（GH-4）与事件归并
「先算后发」（GH-17）。本分支已把这两批改动合入：`AudioRuntime` 的采集侧、
`kernel`/`state` 的归并路径与 `state.rejected` 事件都来自 main，本条的改动只在
**播报侧**（`Response.approval_id/kind`、`abort_response`、`_response_payload`）与
`/v1/robot/announce` 路由上，两边没有语义重叠。合入后本条的全部用例仍通过。

- 不在 robotd 保存审批状态；
- 不在本条实现语音确认/一次性授权签发（#11 与 #18）。
