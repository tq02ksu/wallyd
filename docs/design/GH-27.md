# GH-27 澄清建 run 的语义修正：澄清不建 run，停止不受忙限制

## 1. 问题与证据

`agentd/src/agentd/service.ts` 的 `POST /api/run` 在路由返回 `clarify` 时也调用
`runs.submitRun({ route: 'clarified' })`，且没有带 `status`，因此落成默认的
`accepted`——一个**非终态**。`runs.activeRun()` 会把任何非终态 run 视为活动任务，
而 `executeFastRun` 只在 `kind === 'matched'` 时调用，于是这条 run 永远不会推进：

1. 说一句需要澄清的话 → 库里留下 `accepted` 的 `clarified` run；
2. 紧接着说「停」→ `E_BUSY` 在 `matchRoute` 之前就抛出，连路由都没跑；
3. 只有下一条终态 run 或进程重启才能解除，且重启会把它标成 `interrupted`
   （一条假故障）。

`matchRoute` 的 `ambiguous` 分支同样落到 `route: 'clarified'`，是同一个缺陷。

## 2. 决策

采用 issue 中的**方案 B**：`clarify` / `ambiguous` 不创建 run。

理由：

- **没有执行意图就不该有 run。** run 表示「要执行的一次任务」；澄清是对话上的追问，
  没有副作用、没有可推进的步骤。方案 A 只是把 `accepted` 换成 `waiting_input`，
  `activeRun()` 仍会命中，必须再改忙判据，且库里仍会积累永不推进的 run；
  方案 C 则会在每次重启时把遗留 run 报成 `interrupted`。
- **事件语义已有落点。** issue 担心方案 B「需要一个新事件类型」；实际
  `agentd/contracts/events.json` 早已登记 `route.clarify`（category `route`，
  title「没听明白要做什么」，payload `reason` / `advice`，另可带结构化 `data`）。
  澄清写入这条事件，带 `session_id`（有会话时）与 `data.missing` / `data.fast_rule`，
  因此不需要新增事件类型，也不需要扩张事件白名单。
- **会话仍然连续。** 有 `session_id` 时，用户那句话仍写进该会话的消息表（`run_id` 为空），
  澄清事件与会话消息在同一个事务里提交，界面与历史都不会丢掉这句话。

对契约的影响（issue 已列明这是方案 B 的代价）：`RunAccepted.run_id` / `status`
改为可空——`route=clarified` 的响应不再有 `run_id`。前端在收到澄清时把
`clarify.question` 显示在输入卡上，而不是跳转到任务详情。

## 3. 停止旁路

issue 验收判据 2 要求「停止是安全旁路，不受忙限制」。当前 `E_BUSY` 在 `matchRoute`
之前，受保护的 `stop_robot` 规则根本没有机会命中。修正后的顺序：

```text
matchRoute
  ├─ clarify / ambiguous → 记录 route.clarify，返回澄清（不建 run，不占用名额）
  └─ matched / none
       ├─ 匹配的是受保护规则（stop_robot） → 跳过忙检查，照常建 run 并执行
       └─ 其他 → activeRun() 命中则 E_BUSY（活动上限 1 的纪律不变）
```

`routeCtx.busy` 现在传入真实的 `activeRun()` 结果，而不是写死 `false`——规则前提看到的是
真实状态；受保护规则在该前提下仍优先（`matchRoute` 的先跑顺序本来就是这么设计的）。

**范围之外（本轮不做）**：文本「停」走快速路由时，不取消当时那条活动 run；那属于
`/api/stop` 的职责与 V08 的确认窗口。本 issue 只保证「停」本身不被 `E_BUSY` 拦下。

## 4. 重启对账

方案 B 下不会再有澄清类 run。但升级前的库里可能已经躺着 `route='clarified'` 的非终态 run，
`reconcileOnStartup()` 会把它们报成 `interrupted`（假故障）。对账因此增加一条：
非终态且 `route='clarified'` 的遗留 run 标记为 `cancelled`（从未执行过，无副作用），
写 `run.finished` 且 `outcome=cancelled`、severity `info`，不计入 `daemon.recovered`。

## 5. 测试计划

| 判据 | 证据 |
| --- | --- |
| 1. 澄清后「停」不被 `E_BUSY` 拦 | `agentd/tests/unit/run-request.mjs`：`过来` → `route=clarified`、无 `run_id`、runs 表 0 条；紧接着 `停` → `route=fast`、执行注入的 `executeFast` |
| 2. 忙时「停」仍可达 | 同上：先建一条 `waiting_confirmation` 的活动 run，再提交 `停` → 不抛 `E_BUSY` 且真的下发；同时普通请求仍 409 |
| 3. 连续 3 次澄清不卡 run | 同上：3 次 `过来` → runs 表新增 0 条、`route.clarify` 事件 3 条 |
| 4. 重启不把澄清 run 报成 interrupted | `agentd/tests/unit/runs.mjs`：遗留 `clarified/accepted` run 经 `reconcileOnStartup()` → `cancelled`，`interrupted=0` |

契约先行：`agentd/contracts/openapi.yaml` 的 `RunAccepted` 先改，
再 `npm run contract:agentd` 重新生成 `agentd/contracts/generated/*`。

## 6. 遗留风险

- `idempotency_key` 不再作用于澄清请求（没有 run 可去重）。澄清没有副作用，
  重复只会多一条 `route.clarify` 事件；若将来需要抑制，应给事件加去重键，而不是给澄清造 run。
- 忙时提交澄清请求会返回澄清而不是 `E_BUSY`；它不执行任何动作，也不占名额，因此不违反活动上限。
- 本工作树尚未包含 V05 的三条规则（PR #26 未合并），因此验收里「过来 track:t7」的
  `waiting_confirmation` 场景用一个带前提的自定义规则在单测中复现；不修改 `matchRoute`。
