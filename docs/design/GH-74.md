# GH-74 robotd 串口接入与最小位移原语（离线段）

## 1. 目标与边界

只做 issue 的 `[离线]` 判据 1–4，目标是让「语音 → 动作」在动作这一端**有一条可证明的链路**：

- `robotd` 真的打开一个串口设备（`--serial/--port` 指定，默认值不变），打开失败必须可观测；
- 一条原语能力 `robot_move`：直线距离（mm）+ 速度（mm/s），开环下发，不做闭环/导航/避障；
- `agentd` 的一条快速规则：带明确距离的「往前走 30 厘米」不进 Harness；
- `robot_stop` 在串口已打开时真的写出停机帧，且停止后不再有新帧。

明确不做（与 issue 一致）：闭环控制 / PID / 里程计 / SLAM / 避障、跨帧跟踪与人体检测、
R11 的全量板侧协议（应答关联之外的校验/重传）、看门狗时限、真机操作（判据 5–7）。

## 2. 决策

### D1 串口走 `communication-protocol.md` §3 的 JSON-Lines，不另立协议

每行一个 JSON 对象：命令 `{"id":N,"op":"move","args":{...}}`，应答 `{"id":N,"ok":true,"data":{...}}`，
失败 `{"id":N,"ok":false,"err":{"code","msg"}}`，板侧推送 `{"ev":"motion.done",...}`。
`id` 由 host 单调递增，板侧原样回填；`stop` **不带 id**（契约规定的最高优先级命令）。

单位遵守 ADR-0004 的单点声明：板侧只认 `hello` 声明的**米 / 米每秒**。
公开能力用毫米级参数（issue 的「距离（mm）」），换算发生在 robotd 的板侧边界内，
板侧帧里不会出现 mm/mm/s。

### D2 打开失败：显式失败态，而不是静默跳过

串口打不开（设备不存在、权限不足、路径不是设备）时：

- `robotd` 打印一条 `ERROR`，并在 `App` 上记录 `device_error`；
- 状态进入 `devices.esp32 = "error"`，并发出 `device.changed{device:"esp32",state:"error",reason:...}`；
- `GET /v1/health` 带 `device_error`，`esp32` 为 `error`；
- 之后的 `robot_move` 返回 `503/E_UNAVAILABLE`（带原因），**不写任何一帧**。

选择「降级并继续提供 health/stop」而不是直接退出：判据 1 要求失败原因在 health/事件里可见，
且现场排障时还需要能读状态。注意这不是「假装就绪」——`link_ready` 始终为 false，
能力调用一律被拒绝。`hello` 阶段失败仍沿用既有语义（启动失败、清理后抛错）。

### D3 `robot_move` 是同步下发原语，不声称「到位」

ADR-0004 的红线：开环下没有「已到位 / 物理静止 / 堵转」的事实。因此：

- 请求 `{distance_mm, speed_mm_s?}`（`speed_mm_s` 契约默认 150，范围 50–400）；
- 响应 `{ok, dispatched, distance_mm, speed_mm_s, board_ack}`，语义是「帧已写出、板侧已应答受理」；
- **不创建任务、不推进 progress**：没有结束事实就不可能诚实地终结一个任务；
- 板侧正在执行另一段运动时返回 `409/E_BUSY`（不排队、不重发——物理动作禁止自动重试）。

`task_id` / 任务生命周期留给有完成事实的能力（含后续 `robot_follow`）。
公开名为 `robot_move`（`docs/layers-and-modules.md` 里规划的名字），参数按 issue 定为
`distance_mm` / `speed_mm_s`；`docs/architecture.md` §8.6 的 `left_m/right_m/speed_mps`
是示意草图，不是 OpenAPI 契约，本票以 issue 的参数为准。

### D4 物理动作仍然过审批门

`robot_move` 标 `x-requires-approval.params: [distance_mm, speed_mm_s]`（architecture §10.6：
物理动作默认需审批）。agentd 的快速规则只负责「命中能力并抽参」，审批仍由能力契约驱动：
先说「向前直行一段距离：距离三百毫米，速度一百五十毫米每秒」，用户确认后才下发。
审批词表新增 `distance_mm`（毫米）与 `speed_mm_s`（毫米每秒）两个字段。

### D5 `robot_follow` 本轮不动 —— 判据 4 依赖 #68

判据 4 要求「`robot_follow` 不再是 `UNIMPLEMENTED`，且失效 track 返回 `400/E_VALIDATION`」。
track 存活校验的绑定表由 #68（PR #71）实现，尚未进入 main；维护者在 issue 评论里明确要求
本轮**不要动 `person-bindings.ts`、不要重写 `run-request.ts` 的 GH-68 接缝、不要自己实现绑定表**。
robotd 自身没有视觉/跟踪，无法独立判断 track 是否存活——把 `UNIMPLEMENTED` 摘掉而不提供
存活校验，就是在「假装在跟」。因此本轮保留 `UNIMPLEMENTED`，判据 4 记为 blocked，
待 #68 合入后在同一分支完成：robotd 接 `robot_follow`（持续前进/转向的降级档）+ agentd
沿用 `target_gone → 400/E_VALIDATION`。

### D6 停机接线

`robot_stop` 的本地部分（取消运动任务、写 `safety.stop_requested.cause`）已在 #57 落地。
本轮只补最后一跳：串口打开时 `App.request_stop()` 的 `board.notify("stop")` 现在真的写出
无 id 的 `{"op":"stop"}` 帧；链路断开时如实返回 `board_ack: false`（HTTP 504），
不把「本地已停」说成「物理已停」。`robot_move` 是单帧原语，停止后不存在继续发帧的控制循环。

## 3. 证据与判定

| 判据 | 判定 |
| --- | --- |
| 1 打开失败可观测 | `robotd/tests/unit/test_serial_board.py`：不存在/非设备路径 → `E_UNAVAILABLE` 带原因；`test_app_serial.py`：`device_error` + `device.changed` + health，`move` 被拒且零写入 |
| 2 句子 → 串口字节 | `agentd/tests/unit/move-chain.mjs`：路由抽参 → HTTP 体 `{distance_mm:300,speed_mm_s:150}`；`agentd/tests/integration/approval-cross-check.mjs`：agentd 真签发凭据 → robotd 真验签（数值参数摘要两端一致）；`robotd/tests/unit/test_serial_board.py` / `test_serial_pty.py` 断言 `{"id":2,"op":"move","args":{"left":0.3,"right":0.3,"speed":0.15}}\n`；`robotd/tests/integration/test_move_serial_e2e.py` 用真 pyserial + pty 串起「审批凭据 → HTTP → 串口字节」 |
| 3 停机帧 | 同上：`{"op":"stop"}\n`（无 id），停止后写入计数不再增长（e2e 测试也覆盖） |
| 4 follow | 未做，见 D5；轮次以 `needs-input` 交回 |

真机判据 5–7 不在本轮：它们需要板子在位与人现场测量，由 `hardware` 段执行。
